2. 현재 Agent 작동 흐름

사용자 질문 → SafetyEnvelope → HCX-007 Intent → Ontology·Lexical → 미해결 의미만 Schema Dense·HCLX Resolver → Typed QueryPlan 검증 → 제공 DB 후보 고정 → SQL/Python → 필요 시 공식 외부 검색·Document Dense → 제공 DB 교집합 → Verifier → HCX-007 grounded answer

HCLX Intent ONTyped Alias RegistrySchema Dense ON HCLX bounded Resolver ONDocument Dense ONOfficial Live Search ON DB Intersection ONGrounded Answer ON

  • 명확한 조건은 Ontology·Lexical(규칙·용어 사전 기반 해석)로 잠그며, Dense(Embedding 유사도 검색)와 HCLX는 남은 표현의 제한된 후보만 다룬다.
  • Dense와 HCLX는 상품군·hard filter·정렬 방향·limit를 바꾸거나 후보 밖 field를 만들 수 없다.
  • 외부 근거가 필요한 경우 공식 출처로 제한해 검색하고, 외부 문서에서 확인된 상품과 주최측 제공 DB 상품의 교집합만 답한다.
  • 교집합 없음은 NOT_FOUND, 검색 장애·근거 부족은 CANNOT_VERIFY, 복수 해석은 CLARIFY, 정책 위반은 UNSUPPORTED로 구분한다.
  • HCLX는 Intent 분석과 최종 문장 생성에 참여하지만 SQL 결과·수치·순위·근거를 새로 만들거나 변경하지 못한다.

형식상 개선 필요 40건: 외부 근거까지 확인했지만 제공 DB 교집합이 비어 있는 문항에서 Gold가 빈 결과를 pd_itm_no IN []로 표현한다. 이는 답변 상태·상품·근거에는 올바르지만 실제 SQL로 실행할 수 없는 QueryPlan 표기다. 현재 비교기는 “실행 결과 후보 0·반환 상품 0” 증거가 있을 때만 이 표기를 정규화한다. 향후 Gold를 실행 가능한 계획 계약으로 재사용한다면 별도 EMPTY_INTERSECTION 결과로 수정해야 한다.

6. Phase 4에서 해결한 핵심 병목

  1. 복합 상품군 QueryPlan: 한 질문의 여러 상품군·조건을 단일 계획으로 뭉개지 않고 family_searches 하위 계획으로 보존했다.
  2. Semantic Coverage Gate: 식별자·ranking·기간·hard filter 중 하나라도 해석되지 않으면 조건을 버리고 실행하지 않도록 질문 전체 의미 포함 범위를 검사한다.
  3. 정확 상품 식별자: 상품코드·ticker·ISIN·정확 상품명을 일반 키워드보다 우선하고, 한국어 조사와 붙은 코드도 분리한다.
  4. 정렬 가능 값 정책: 0·결측은 수익률·보수 등 정렬 기준에서 제외한다. 외부 교집합은 존재하지만 정렬 가능한 값이 없을 때 상태를 잘못 NOT_FOUND로 바꾸지 않는다.
  5. Schema Dense 계약: KURE-v1 index와 calibration의 threshold 불일치를 사전 점검에서 발견해 margin 0.042771의 v5 index로 다시 동결했다.
  6. HCLX Resolver 권한: HCLX 선택은 Dense 후보 안으로 제한하고, 질문 원문의 evidence span과 deterministic anchor가 모두 맞을 때만 서버가 승인한다.
  7. 공식 외부 근거: Document Dense로 공식 URL 후보를 찾고, 공식 원문·발행일·기간·관계·제공 DB 교집합을 확인한 뒤에만 상품을 반환한다.
  8. 평가 Comparator: NOT_FOUND/CANNOT_VERIFY, 교차 상품군, 빈 교집합, derived metric을 실제 실행 증거에 맞춰 엄격하게 비교한다.

9. 남은 필수 작업

  1. 새 미공개 holdout: Phase 4 수정 사항을 동결한 뒤 새로운 질문으로 일반화 성능을 한 번 더 측정해야 한다. 현재 100%는 회귀 성능이다.
  2. Gold 계약 정리: 40건의 빈 IN [] 표기를 실행 가능한 빈 교집합 결과 계약으로 바꿔야 한다.
  3. 배포 artifact 포함: v5 Schema Dense index와 v16 calibration은 현재 .gitignore 대상이다. 추후 승인된 commit에서 두 파일만 명시적으로 강제 stage해야 한다.
  4. Clean Release 동결: 검토·commit 후 같은 commit으로 최소 Docker image, image digest, DB·Ontology·Schema Dense·Document Dense·relation·prompt hash를 하나의 Release Manifest에 결합해야 한다.
  5. 최종 NCP 검증: 사용자가 “최종 버전”이라고 명시적으로 승인한 뒤에만 NCP에 배포하고, 공인 IP의 /health·공식 GET /answer·Rollback·순차 p50/p95/p99를 마지막으로 확인한다.

현재 가장 안전한 다음 단계는 이 dirty working tree를 팀 검토 가능한 단위로 정리한 뒤, 새 미공개 질문을 추가 수정 없이 최초 1회 실행하는 것이다. 검증되지 않은 새 기능을 더 얹을 단계는 아니다.
