# Qwen 변형 질문·전체 Agent 스트레스 평가

상태: v1.1 공개 개발 회귀 · 독립 blind 아님

기준일: 2026-08-08

## 0. 한눈에 보기

기존 질문을 그대로 반복해서 100점을 받는 것만으로는 처음 보는 표현에 잘 대응하는지
알 수 없다. 로컬 Qwen이 공개 모의 질문 30개를 세 방식으로 바꿔 90개를 만들고,
의미가 보존된 질문만 실제 Agent 전체 경로로 실행했다

| 항목 | 결과 |
| --- | ---: |
| 원문 질문 | 30개 |
| Qwen 생성 후보 | 90개 |
| 숫자·식별자·의미 보존 검사 통과 | 77개 |
| 실행 전 폐기 | 13개 |
| 결정론적 Agent strict | 77/77 |
| Qwen 계획·답변 포함 전체 Agent strict | 77/77 |
| 원문과 실행 결과 동일 | 77/77 |
| 안전 규칙 통과 | 77/77 |
| Qwen 답변 fallback | 개선 전 3/61 → 개선 후 0/61 |

이 결과는 “공모전에서 100점”이라는 뜻이 아니다. AI 담당자가 만든 공개 질문에서
파생했고 실패를 보며 코드를 개선한 사후 회귀다. 의미가 바뀐 13개도 분모에서 숨기지
않고 생성 품질 지표로 따로 기록한다

## 1. 무엇을 시험했나

Qwen은 질문마다 다음 세 표현을 하나씩 만들었다

- `paraphrase`: 뜻은 같게 두고 표현만 바꿈
- `clause_reordering`: 조건의 순서를 바꿈
- `distractor_resistance`: 답 형식 같은 무해한 부가 문장을 붙임

실행 전 validator는 숫자, 상품 ID·티커, 비교 연산자, 핵심 금융 개념과 상품군이
원문과 같은지 검사한다. 하나라도 달라지면 Agent에 넣지 않는다. 생성 모델이 만든
질문을 생성 모델 스스로 정답이라고 선언하지 못하게 하는 경계다

```text
공개 원문 30개
  → Qwen 변형 90개
  → 의미 보존 검사
      ├─ 실패 13개: 실행하지 않고 생성 품질 실패로 기록
      └─ 통과 77개
           → Router·QueryPlan·Oracle·Result Verifier
           → field evidence·Qwen 답변·Answer Verifier
           → 원문 실행 지문과 비교
```

## 2. 첫 실행에서 발견한 문제

| 단계 | 통과 | 의미 |
| --- | ---: | --- |
| 최초 Qwen 생성·결정론적 Agent | 60/88 | 변형 validator가 허용한 질문 중 28개가 기존 문장 경계를 벗어남 |
| 엄격한 생성 선별 후 | 59/77 | 의미 보존 77개를 고정했지만 Agent 표현 처리 공백이 남음 |
| Agent·gold 감사 후 결정론적 경로 | 77/77 | 네 상품군에서 원문과 동일한 실행 결과 확인 |
| Qwen 계획·답변 전체 경로 | 77/77 | 실제 모델을 넣어도 검색·근거·안전 계약 유지 |

발견한 문제를 단순히 prompt로 덮지 않고 Router, linker, 비교·집계 parser의 공통
문법과 안전 회귀로 옮겼다. 대표 보강 범위는 `상품 수 계산`, `연금으로 거래 가능`,
`잔존일수 짧은 순`, 숫자로 시작하는 해외 상품 ID, 공모펀드의 항목 우선형 비교
문장과 표·목록 응답 형식 문구다

## 3. 평가 정답도 검증 대상임

변형 질문이 같은 두 문항에서 일관되게 기존 정답과 다른 결과를 냈다. DB 값을 직접
재검사하자 기존 정답이 질문의 정렬 방향과 반대로 기록돼 있었다

| 문항 | 질문 의미 | 기존 정답 | 교정 |
| --- | --- | --- | --- |
| 009 | 총보수율 낮은 순 | 내림차순 상위 상품 | 유효 총보수율 오름차순 상품 |
| 016 | 잔존일수 짧은 순 | 잔존일수 내림차순 상품 | 현재 매수 가능 채권의 잔존일수 오름차순 상품 |

과거 suite와 report는 수정하지 않았다. 별도
`official-mock-v1-gold-audit-v1`을 만들고 원문 suite와 정규화 DB SHA-256이 정확히
같을 때만 두 교정을 적용한다. 모델뿐 아니라 평가 정답도 감사해야 한다는 실험
사례로 보존한다

## 5. Qwen 역할을 나눠 본 ablation

같은 질문과 데이터에서 Qwen을 쓰는 위치만 바꿨다. 모델 없는 답변 provider도
호출 수 계측에는 포함되지만 실제 LLM 네트워크 호출은 아니다

| Qwen 사용 위치 | strict | 실제 Qwen 계획 | 실제 Qwen 답변 | p50 | p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 사용 안 함 | 77/77 | 0 | 0 | 75.116ms | 1,069.531ms |
| 질문 계획만 | 77/77 | 43 | 0 | 336.677ms | 2,939.420ms |
| 근거 답변만 | 77/77 | 0 | 61 | 1,193.250ms | 2,287.549ms |
| 질문 계획+근거 답변 | 77/77 | 43 | 61 | 1,226.605ms | 4,096.584ms |

공개 회귀에서는 네 방식의 정확도가 같았다. 이미 서버 규칙이 이해하는 질문에
모델을 추가하면 지연과 호출량만 늘어난다는 뜻이다. 반대로 이 결과만으로 Qwen 계획이
불필요하다고 결론 낼 수는 없다. 다음 독립 표현 세트에서 서버 규칙이 놓치지만 모델은
이해하는 질문이 얼마나 되는지 따로 측정해야 한다

HyperCLOVA X 연결 후에는 모든 요청에 같은 호출을 강제하지 않고 다음 후보를 A/B한다

- 명확한 상세·비교·집계·제어 요청은 서버 compiler로 바로 처리
- 규칙이 충분히 이해한 SEARCH는 HCX 계획 호출을 생략할 수 있는지 검토
- 자연어 해석이 필요한 SEARCH만 HCX 계획을 호출하고 grounding gate로 검증
- 설명이 실제로 필요한 결과만 HCX 답변을 호출하며 계산 결과는 결정론적으로 제공

## 6. fallback 3건을 0건으로 줄인 방법

개선 전 Qwen 답변 61건 중 같은 국내채권 질문 계열 3건이
`deterministic_fallback`으로 전환됐다. Qwen이 “매수수익률은 수익성 평가에 사용된
지표”라고 썼고, Answer Verifier가 `수익성 평가`를 가치판단 가능 표현으로 차단했다

검증기를 느슨하게 하지 않았다. 대신 서버가 질문 유형에 맞는 안전한 설명문을
구조화 출력 schema로 제공하고 모델이 그대로 복사하게 했다. 상품명·수치·순위·
기준일과 출처는 계속 서버가 evidence에서 컴파일한다

- 개선 전: 3/61 fallback, 답변 호출 기준 4.918%
- 개선 후: 0/61 fallback
- strict·safety·evidence: 개선 전후 모두 100%

이 방식은 모델이 바뀌어도 사용할 수 있어 HyperCLOVA X 연결 후 같은 A/B 비교를
수행할 수 있다

## 8. 다음 평가

이 세트는 표현 변화에 대한 강건성은 보여 주지만 독립 질문은 아니다. 다음 순서는
기존 30문항에서 파생하지 않은 공격 질문을 별도로 만들고, 질문과 정답을 봉인한 뒤
최초 실행을 보존하는 것이다. 이후 같은 세트를 HyperCLOVA X로 재생해 Qwen과의
계획 정확도·fallback·지연·호출량 차이를 비교한다

## 9. 원문 표현을 숨긴 semantic round-trip

위 77문항은 Qwen이 기존 질문 문장을 보고 바꿈 질문이다. 더 어려운 시험을 위해
다음 실험에서는 **기존 질문 문장을 Qwen에게 보여 주지 않았다**. 서버가 확정한
상품군·조건·정렬·비교·집계 의미만 주고 정중한 문장, 구어체, 전문 메모 형식의
새 질문을 다시 만들게 했다

| 항목 | 결과 |
| --- | ---: |
| 새 질문 생성 요청 | 75개 |
| 생성 완료 | 75개 |
| 숫자·식별자·연산자·의미 보존 통과 | 64개 |
| 실행 전 폐기 | 11개 |
| 결정론적 Agent 최초 실행 | 15/64 |
| 근거 첨부 Qwen 계획 최초 실행 | 28/64 |
| 공통 문법 보강 후 출력·QueryPlan 모두 동일 | 64/64 |
| 최종 safety·evidence | 각각 64/64 |

최초 15/64를 숨기지 않고 보존했다. 이 실패로 조건의 순서가 바뀐 문장,
자연어 상품 식별자, 공모펀드 비교, 집계 표현에서 공통으로 쓸 수 있는
규칙을 찾았다. 특정 64문장을 하나씩 외우는 예외 처리로 고치지 않고 Router,
linker, 비교·집계 parser의 공통 언어 규칙으로 옮겼다

### 우연히 같은 답이 나오는 것도 실패로 처리

초기 평가는 검색된 상품·수치가 같은지 중심으로 비교했다. 그러면 불필요한 조건을
추가했거나 조건 하나를 빼도 우연히 같은 상품이 나오면 통과할 수 있었다

이후 다음 항목을 평가 지문에 추가했다

- 상품군·질문 유형·조건·정렬·비교 항목·집계 함수가 원문과 같은지
- 순서가 의미 없는 조건 목록은 정렬한 뒤 해시하고, 정렬 우선순위는 그대로 보존
- `question_id`처럼 질문마다 바뀌지만 실행 의미와 무관한 값은 제외

이 기준을 처음 적용하자 기존 64/64가 59/64로 떨어졌다. 즉 출력은 같았지만
내부 계획은 다른 5건이 있었다. 해당 문법을 교정한 뒤에는 강화된 기준에서도
64/64를 확인했다

### Qwen은 계획을 제안하고, 서버가 실행 권한을 판정

기존 Qwen QueryPlan은 JSON 형식만 맞으면 너무 많은 의미 권한을 가질 수 있었다.
새 `grounded plan` 경로는 모델이 조건·정렬·비교·집계를 제안할 때마다 사용자
원문에서 그 근거를 그대로 복사해 붙이게 한다

서버는 다음을 모두 확인한 제안만 실행한다

- 근거 문구가 질문에 실제로 연속해 존재
- 해당 필드가 그 상품군에서 검색·정렬·비교·집계 가능
- 숫자·불리언·연산자·정렬 방향이 근거 문구와 일치
- 상품 코드가 원문에 있고 전체 데이터에서 단 하나로 확정
- 서버가 이미 확정한 조건·정렬·비교·집계를 모델이 빼지 않음
- 예측·단정 추천·미지원 조건은 모델이 구제하지 못함

최초 gate 감사에서 실행 후보 63건 중 Qwen은 유효한 구조 46건을 냈고,
gate는 14건만 받았다. 이 중 9건은 기존 규칙 경로가 못 풀던 질문을 구제했고
4건은 기존 계획에 원문으로 입증된 정보를 더했다. 나머지는 서버 계획으로 돌아가거나
안전하게 역질문했다. 이 수치는 관대한 모델 수용률이 아니라, **모델이 잘못해도
정답 권한을 얻지 못하는 비율**을 보기 위한 감사다

최초 Qwen grounded-plan은 28/64까지 올렸지만, 그 결과를 보고 prompt·gate를
강화했으므로 같은 frozen batch의 Qwen 재실행은 아직 남아 있다. 재실행 전에 28/64를
최종 모델 성능으로 표현하지 않는다
