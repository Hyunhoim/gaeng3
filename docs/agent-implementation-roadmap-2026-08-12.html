1~9단계 구현 방향 로드맵

예선의 핵심인 안전성·정확성·저지연을 먼저 지키고, 이후 Schema Dense·HCLX·Product Dense를 검증된 경계 안에 단계적으로 연결하는 구현 가이드다. 각 단계는 독립적으로 테스트하고 되돌릴 수 있어야 하며, 이전 단계를 통과하기 전에는 다음 기능을 운영 경로에 활성화하지 않는다.

기준일 2026-08-12 문서 종류: 구현 방향 가이드 대상: 팀원 공유용 범위: 단계 1~9 상태: 완료 보고서 아님
한눈에 보기 공통 원칙 1~3단계 4~6단계 7~9단계 진입·배포 기준 용어 후속 문서 원칙

1. 한눈에 보는 구현 방향

핵심 결론: 기존 SafetyEnvelope와 결정론적 SQL·Python·Verifier 경계는 유지한다. 새 모델은 모두 후보 또는 계획을 제안할 뿐이며, 서버가 승인한 ValidatedPlan만 실제 상품 데이터 조회에 사용할 수 있다.
유지

Fast Path

완전히 명확한 질문은 HCLX·Dense 없이 기존 규칙과 SQL로 처리한다.

오프라인

Schema Dense

사용자 표현을 field 후보에 연결한다. 현재 운영 경로에는 연결하지 않는다.

확장 설계

Product Dense

실서비스에서 SQL 후보 안의 의미 검색을 담당할 모듈 골격만 준비한다.

현재 미사용

Vector DB

필요성이 측정되기 전에는 도입하지 않는다. 작은 Schema index는 exact 검색이 우선이다.

2. 모든 단계에 적용할 공통 원칙

모델은 실행 권한이 없다

  • Dense는 field 또는 product ID 후보만 제안한다.
  • HCLX는 허용된 field 안에서 Typed QueryPlan만 제안한다.
  • Raw SQL, DB 경로, credential, 자유로운 tool 호출을 모델에 주지 않는다.

모호하면 추측하지 않는다

  • 실제 조건 누락은 CLARIFY로 종료한다.
  • 제공 데이터 밖 기능은 UNSUPPORTED로 종료한다.
  • Dense top-1이나 HCLX confidence를 실행 근거로 사용하지 않는다.

수치와 상품은 DB가 확정한다

  • 수익률·보수·가격·정렬·집계는 SQL/Python이 계산한다.
  • 모델 검색 후에도 최종 product ID와 수치는 원천 DB에서 재조회한다.
  • Verifier 실패 결과는 성공 응답으로 반환하지 않는다.

활성화는 단계적으로 한다

  • off → shadow → canary → enforce 순서를 지킨다.
  • shadow는 기록만 하고 응답·SQL에는 영향을 주지 않는다.
  • 기능별 독립 blind 평가와 rollback 경로가 있어야 다음 단계로 간다.

3. 1~3단계 — 실행 경계부터 고정

1

PlanningDecision을 Shadow로 추가

질문이 어떤 경로로 가야 하는지 서버가 먼저 분류하되, 아직 기존 응답에는 영향을 주지 않는다.

첫 구현
쉬운 설명: “바로 검색할 질문”, “표현만 새로워 Dense가 도울 질문”, “조건이 빠져 역질문할 질문”, “처리하면 안 되는 질문”을 먼저 구분하는 교통정리 단계다.
추가할 분류

TRUE_AMBIGUITY, SCHEMA_LINK_GAP, UNSUPPORTED, NONE

추가할 권한

dense_allowed, hclx_allowed, sql_allowed를 서버가 결정한다.

세부 구현 지침
  • PlanningDecision 내부 DTO에 policy version, path, semantic issue, unresolved span, product family, reason code를 담는다.
  • 금지·범위 밖 질문은 Dense·HCLX·Compiler·Oracle 호출 권한을 모두 false로 고정한다.
  • “수익률 좋은 ETF”처럼 기간이 빠진 질문은 Dense가 의미를 대신 정하지 못하게 즉시 CLARIFY한다.
  • 처음에는 adaptive_shadow로 판단만 기록하고 현재 Router 결과와 응답을 그대로 사용한다.
  • 영향 예상: semantic_gate.py, router.py, 신규 planning_policy.py, 무호출 테스트.
완료 기준
  • 기존 명확 질문의 QueryPlan·상품 ID·수치 fingerprint가 완전히 동일하다.
  • 금지 질문에서 Compiler·Dense·HCLX·Oracle 호출이 모두 0회다.
  • 실제 모호성과 Schema Link Gap이 서로 다른 reason code로 기록된다.
  • Planning Policy 오류 시 기존 fail-closed 경로로 종료한다.
3줄 요약
  1. 질문을 명확·표현 미해결·실제 모호·미지원으로 먼저 나눈다.
  2. 처음에는 기록만 하고 기존 답변과 SQL 실행은 바꾸지 않는다.
  3. 금지·실제 모호 질문은 Dense·HCLX·Oracle을 호출하지 않는다.
2

제안 계획과 실행 가능 계획을 분리

ProposedQueryPlan → PlanAuthorityGate → ValidatedPlan → Oracle 경계를 타입으로 강제한다.

핵심 경계
쉬운 설명: 모델이나 규칙이 만든 계획은 “신청서”일 뿐이다. 서버 검사를 모두 통과해 “실행 허가증”을 받은 계획만 DB 조회에 사용할 수 있게 만든다.
ProposedQueryPlan

아직 신뢰하지 않는 계획이다. HCLX 또는 서버 규칙이 만들 수 있지만 실행할 수는 없다.

ValidatedPlan

field·연산자·단위·dataset·권한·budget 검사를 모두 통과한 서버 발급 실행 객체다.

세부 구현 지침
  • ValidatedPlan은 frozen·extra-forbid 형태로 만들고 내부에 canonical QueryPlan과 검증 영수증을 담는다.
  • 영수증에는 plan hash, planning/capability/ontology/registry/dataset/compiler/verifier version과 deadline·row budget을 넣는다.
  • PlanAuthorityGate가 field 존재, queryable/sortable/aggregatable, operator, type, unit, period, direction, limit, 승인 dataset을 검사한다.
  • SQLiteOracle.execute()와 Aggregate Oracle은 장기적으로 ValidatedPlan만 받게 한다.
  • 공개 Backend DTO는 바꾸지 않고 Core 내부 계약으로 먼저 도입한다.
완료 기준
  • 일반 QueryPlan을 Oracle에 전달하는 우회 테스트가 실패한다.
  • 모호성·미지원 조건이 하나라도 남으면 ValidatedPlan이 발급되지 않는다.
  • 기존 SEARCH·COMPARE·AGGREGATE의 결과와 근거가 변하지 않는다.
  • ValidatedPlan의 release·snapshot 정보만으로 실행 조건을 재현할 수 있다.
3줄 요약
  1. QueryPlan을 만들었다고 바로 실행하지 않고 서버 검증을 다시 거친다.
  2. 모든 검사를 통과한 ValidatedPlan만 Oracle에 들어갈 수 있다.
  3. 이 경계가 완성돼야 Dense와 HCLX를 안전하게 연결할 수 있다.
3

AgentReleaseManifest로 버전을 하나로 묶기

Ontology·Field Registry·Dataset·Prompt·Model·Index가 서로 다른 버전으로 섞이지 않게 한다.

코드 경계 구현
쉬운 설명: DB는 어제 버전인데 Dense index는 오늘 버전인 상태를 막는다. Image 안의 AgentReleaseManifest와 push 후 만드는 외부 DeploymentBinding을 연결해 순환 참조 없이 한 release로 묶는다.

세부 구현·완료 기준
  • 서버 시작 시 모든 hash를 확인하고 하나라도 다르면 readiness를 실패시킨다.
  • 하나의 요청은 시작부터 답변 완료까지 동일한 release ID를 사용한다.
  • 요청 도중 release 또는 승인 manifest가 바뀌면 실행하지 않는다.
  • 이전 Binding·image·release별 DB volume을 보관하고 실제 배포 환경에서 rollback drill을 수행한다.
  • Field Registry·Dense index, QueryPlan schema·Compiler 불일치 테스트가 모두 fail-closed여야 한다.

현재 애플리케이션 fail-closed 계약과 Docker 배선은 구현됐다. Dirty working tree에서는 공식 manifest 발급을 거부하며, 실제 registry image push·digest 확인·무중단 rollback은 NCP 준비 후 검증한다.

3줄 요약
  1. 데이터·Ontology·Prompt·Model·Index 버전을 release ID 하나로 묶는다.
  2. 버전이나 hash가 하나라도 다르면 서버가 실행되지 않게 한다.
  3. 같은 release와 snapshot으로 같은 실행을 재현할 수 있어야 한다.

4. 4~6단계 — 측정한 뒤 모델을 Shadow로 연결

4

관측·감사 계약 추가

어떤 경로와 모델이 호출됐고 왜 차단·실행됐는지 민감정보 없이 추적한다.

선행 필수
쉬운 설명: Dense와 HCLX를 붙이기 전에 “언제 호출됐고, 얼마나 걸렸고, 왜 실패했는지” 볼 수 있는 계기판과 블랙박스를 먼저 만든다.
운영 Metric

경로별 호출 수, p50·p95·p99 latency, timeout, fallback, verifier 실패, queue·inflight를 집계한다.

Audit Event

request ID, release ID, reason code, plan hash, snapshot, product ID, evidence ID로 실행을 재구성한다.

세부 구현 지침
  • Safety, Planning, Lexical, Dense, HCLX, Compiler, SQL, Verifier, Renderer 단계를 각각 측정한다.
  • 금지 질문의 Dense·HCLX·Oracle 무호출률, 과도한 CLARIFY, evidence completeness를 별도 지표로 둔다.
  • 일반 로그에 API key, Authorization header, DB 경로, blind 정답, Chain-of-Thought를 기록하지 않는다.
  • 원문 질문 보관이 꼭 필요하면 일반 로그와 분리된 암호화·접근통제 저장소를 사용한다.
  • secret·PII fixture가 일반 로그에 나타나지 않는 자동 테스트를 추가한다.
완료 기준
  • request ID 하나로 route·plan·snapshot·verifier 결과를 재구성한다.
  • 금지 질문이 어느 하위 계층도 호출하지 않았음을 지표로 증명한다.
  • 일반 로그의 API key·PII·DB 경로 노출이 0건이다.
  • 관측 시스템 장애가 Agent 성공 응답을 조용히 왜곡하지 않는다.
3줄 요약
  1. Dense·HCLX를 붙이기 전에 호출·지연·차단 이유를 측정한다.
  2. 감사에는 hash와 ID를 남기고 secret·개인정보는 일반 로그에서 제외한다.
  3. 무호출·fallback·Verifier 실패를 자동으로 확인할 수 있어야 한다.
5

Hybrid Schema Linker를 Shadow로 연결

Lexical과 Schema Dense를 함께 사용하되, 미해결 표현의 field 후보만 제안한다.

Shadow
쉬운 설명: 사용자가 데이터 컬럼명과 다른 표현을 썼을 때 비슷한 field를 찾는다. 단, Dense가 고른 1등을 그대로 실행하지 않고 충돌 여부까지 서버가 검사한다.
Schema Dense가 하는 일

“최근 한 달 성과” 같은 표현을 one_month_return_pct 등의 field 후보로 연결한다.

Schema Dense가 하지 않는 일

상품 검색, QueryPlan 확정, 누락 조건 추측, 숫자·정렬 방향 결정은 하지 않는다.

세부 구현 지침
  • 평가 코드와 분리된 운영용 SchemaLinkDecision 계약을 만든다.
  • 결과 상태는 found, conflict, abstain, disabled로 제한한다.
  • 후보에는 field ID, lexical rank, dense score, fused rank, capability, top1-top2 margin, registry/index version을 담는다.
  • 현재 상품군 Field Registry 밖 후보와 intent capability가 맞지 않는 field는 제거한다.
  • 현재 약 100개 field는 Vector DB 없이 exact cosine 전체 비교를 사용한다.
  • 실제 Embedding 모델·revision·license·dimension·전처리를 manifest에 고정하기 전에는 enforce를 허용하지 않는다.
완료·활성화 기준
  • 금지·실제 모호 질문의 Dense 호출이 0회다.
  • Registry·상품군 밖 field가 0건이다.
  • low-margin·분포 밖 표현에서는 실행 대신 abstain한다.
  • 기존 Fast Path 회귀가 0건이다.
  • 독립 blind 표현에서 Lexical 대비 정확도 개선과 latency budget을 모두 충족한다.
3줄 요약
  1. Schema Dense는 사용자 표현을 field 후보에 연결하는 보조 검색이다.
  2. 충돌하거나 확신할 수 없으면 실행하지 않고 abstain·CLARIFY한다.
  3. 현재 규모에서는 Vector DB 없이 exact 검색으로 충분하다.
6

HCLX GroundedPlanProvider를 Fake로 구현

실제 API를 호출하기 전에 제한된 입력·출력·오류·fallback 계약을 테스트 대역으로 완성한다.

Fake Transport
쉬운 설명: HCLX가 자유롭게 SQL을 만드는 것이 아니라, 서버가 허용한 field 카드 안에서만 조건 조합 초안을 작성하게 만든다.
HCLX에 전달할 제한된 Context 
GroundedPlanningContext
- question
- question_id
- product_family
- allowed_field_candidates
- candidate_policy_version
- field_registry_sha256
- capability_matrix_version
세부 구현 지침
  • HCLX에는 전체 DB schema가 아니라 Hybrid Linker가 승인한 field 후보만 enum으로 제공한다.
  • 모든 constraint·ranking·aggregation에 사용자 질문의 원문 evidence_span을 요구한다.
  • 후보 밖 field, 질문에 없는 숫자, 연산자·방향·상품군 변경, 조건 누락은 전체 계획을 거부한다.
  • HCLX에 raw SQL, DB·URL·shell·credential 접근 권한을 제공하지 않는다.
  • 명확한 질문에서는 Provider를 호출하지 않고, 장애 시 서버 Fast Path가 있으면 재사용한다.
  • 서버 계획이 없고 모델 계획도 검증되지 않으면 임의 추론 대신 CLARIFY한다.
완료 기준
  • 명확 질문에서 fake HCLX 호출이 0회다.
  • 복잡한 조건 조합으로 분류된 질문에서만 Provider 호출이 허용된다.
  • schema·field·숫자·operator·direction 변조가 모두 차단된다.
  • Provider 오류가 HTTP 500 또는 미검증 SQL 실행으로 이어지지 않는다.
  • 기존 legacy QueryPlan equality flag를 목표 구조의 완성형으로 사용하지 않는다.
3줄 요약
  1. HCLX는 서버가 승인한 field 후보 안에서만 Typed QueryPlan을 제안한다.
  2. 질문 근거가 없는 숫자·조건·방향을 추가하면 계획 전체를 거부한다.
  3. 실제 API 연결 전에 fake transport로 안전·오류·fallback을 먼저 완성한다.

5. 7~9단계 — 실제 연결·운영·실서비스 확장

7

실제 HCLX를 Shadow로 연결

API Key·HCX-007 권한·공식 응답이 확인된 뒤 실제 계획을 생성하되, 먼저 SQL 실행에는 사용하지 않는다.

Credential 이후
쉬운 설명: 실제 HCLX의 답을 바로 믿지 않고 서버 계획과 나란히 비교하며 정확도·속도·오류를 먼저 측정한다.
품질 측정

product family, field ID, operator, value, unit, direction, 누락·추가 조건을 exact 기준으로 비교한다.

운영 측정

p50·p95·p99 latency, token, timeout, rate limit, malformed, fallback 원인을 분리한다.

보안·운영 지침
  • Provider Egress Gateway를 두고 HCLX에 전송 가능한 DTO를 allowlist로 제한한다.
  • PII, 계좌번호, 카드·인증정보, API key, 내부 경로가 발견되면 외부 전송 없이 종료한다.
  • HCLX 전용 semaphore, connect/read timeout, 전체 deadline보다 짧은 stage budget, Circuit Breaker를 둔다.
  • 실제 모델 계획은 shadow에서 기록만 하고 기존 deterministic 응답과 SQL을 유지한다.
  • 독립 blind 평가와 장애 평가를 통과한 release만 제한 canary로 올린다.
Canary 진입 기준
  • 금지 질문의 HCLX outbound call이 0회다.
  • 미검증 HCLX 결과가 실행 권한을 얻는 경우가 0건이다.
  • Provider 장애 중에도 deterministic Fast Path가 정상 처리된다.
  • 충돌·조건 누락·저신뢰 계획은 모두 CLARIFY로 종료한다.
  • 기존 결정론적 회귀가 0건이다.
3줄 요약
  1. 실제 HCLX 연결 후에도 먼저 계획만 만들고 실행에는 사용하지 않는다.
  2. 정확한 field·조건·방향과 latency·token·오류를 독립 평가한다.
  3. 보안·정확도·fallback 기준을 모두 통과한 일부 유형만 canary로 연다.
8

동시성·Timeout·장애 대응 보강

Dense·HCLX·DB 중 하나가 느리거나 고장 나도 전체 Agent가 같이 멈추지 않게 자원을 분리한다.

운영 준비
쉬운 설명: 요청이 몰리거나 HCLX가 늦어져도 스레드와 메모리가 무한히 쌓이지 않도록, 단계별 제한과 안전한 실패 규칙을 만든다.
장애별 허용 동작
장애허용 동작
HCLX 장애Fast Path 유지, HCLX가 꼭 필요한 질문은 CLARIFY
Dense 장애Lexical 유지, 미해결 표현은 추측하지 않고 CLARIFY
DB manifest 불일치해당 상품군 readiness=false, 실행 금지
Verifier 실패성공 응답 금지
Release hash 불일치인스턴스 기동·트래픽 수신 금지
Overload무한 대기 대신 제한된 오류로 빠르게 거절
세부 구현 지침
  • 요청마다 생성하는 교차 상품군 ThreadPool을 공유 bounded executor 또는 전역 budget으로 교체한다.
  • HCLX·Embedding·DB에 서로 다른 semaphore와 stage timeout을 둔다.
  • timeout 이후 background worker가 계속 capacity를 점유하는지 지표로 노출한다.
  • per-client/IP/global rate limit과 request·row·payload 크기 제한을 둔다.
  • 공식 평가 API 인증 계약이 확정되면 API key·허용 IP·TLS를 별도 배포 계약으로 적용한다.
완료 기준
  • 1×·4×·16× 동시 요청에서 상품 ID·수치·근거가 동일하다.
  • Overload 시 스레드·메모리·queue가 무한히 증가하지 않는다.
  • HCLX timeout이 deterministic Fast Path의 latency를 같이 끌어올리지 않는다.
  • provider·DB·index fault injection 결과가 정해진 fallback matrix와 일치한다.
3줄 요약
  1. HCLX·Dense·DB의 자원과 timeout을 서로 분리한다.
  2. 장애 시 무한 대기하거나 추측하지 않고 정해진 fallback으로 종료한다.
  3. 동시 요청과 fault injection으로 정확성·메모리·queue를 함께 검증한다.
9

실제 미래에셋증권 규모로 확장

현재 안전 계약을 유지하면서 저장소·트래픽·상품 문서 규모에 맞게 실행 인프라를 교체한다.

실서비스 확장
쉬운 설명: 현재 SQLite를 당장 버리는 것이 아니라, QueryPlan과 검증 규칙은 그대로 두고 실제 사내 DB·상품 API·검색 인프라로 갈아 끼울 수 있게 만든다.
ExecutionAdapter

SQLite·PostgreSQL·사내 Product API·Warehouse를 동일한 ValidatedPlan 뒤에 연결하는 교체 지점이다.

ProductRetriever

SQL이 허용한 상품 후보 안에서만 BM25·Product Dense를 실행하는 확장 모듈 계약이다.

Product Dense와 Vector DB 방향 
질문
→ QueryPlan
→ SQL Hard Filter
→ 승인된 CandidateUniverse
→ BM25 + Product Dense
→ 필요한 경우에만 Re-ranker
→ 최종 product ID·수치 DB 재조회
→ Verifier
  • 현재는 ProductRetriever, CandidateUniverse, NullProductRetriever, design-only Index Manifest와 계약 테스트만 준비한다.
  • Product Dense는 수익률·보수·가격을 반환하지 않고 product ID 후보만 반환한다.
  • Schema Dense와 Product Dense의 index·manifest·평가를 서로 분리한다.
  • 전용 Vector DB는 상품·문서 수, SQL 필터 후 후보 수, QPS, p95 latency, 갱신·HA 요구가 실제로 커질 때 검토한다.
  • 초기 Product Dense shadow는 exact 검색 또는 PostgreSQL+pgvector 같은 단순한 실행 계층부터 비교한다.
엔터프라이즈 구현 항목
  • Stateless API replica, load balancer, multi-AZ, read replica, connection pool, blue/green·canary·rollback을 도입한다.
  • 사용자·서비스 identity와 RBAC, row/column 접근정책, Provider outbound 제한을 적용한다.
  • 상품군·시장·지역별 partition과 승인된 serving view를 사용하고 원천 OLTP를 Agent가 직접 조회하지 않게 한다.
  • field evidence는 내부에서 유지하되 외부 응답은 evidence ID 또는 pagination으로 payload를 줄인다.
  • 상품 Finder와 추천·가입·주문 Agent는 identity·권한·감사·승인 체계를 분리한다.
완료 기준
  • SQLite와 새 Adapter가 동일한 canonical 결과를 반환하는 계약 테스트를 통과한다.
  • Product Dense가 CandidateUniverse 밖 product ID를 반환할 수 없다.
  • Product Dense 장애 시 기존 SQL/BM25 결과가 유지된다.
  • 새 index·DB·release rollback과 backup restore가 실제 훈련으로 검증된다.
  • 추천·주문 기능이 Finder 권한으로 실행되는 경로가 없다.
3줄 요약
  1. QueryPlan·ValidatedPlan·Verifier는 유지하고 DB와 검색 인프라만 Adapter로 교체한다.
  2. Product Dense는 SQL 후보군 안에서만 상품 ID 후보를 제안하며 현재는 골격만 둔다.
  3. Vector DB와 Re-ranker는 실제 규모·정확도·latency 필요성이 입증될 때만 도입한다.

6. 단계 진입·배포 승인 기준

0건이어야 하는 보안 불변식: 미검증 QueryPlan 실행, 범위 밖 상품·field 실행, 쓰기 SQL, 금지·실제 모호 질문의 Oracle 실행, PII·secret 외부 전송, Verifier 실패 결과의 success 응답, 승인 manifest 불일치 상태 실행.
1 → 2단계 PlanningDecision shadow가 기존 응답을 바꾸지 않고 무호출 정책을 정확히 기록해야 한다.
2 → 3단계 일반 QueryPlan이 Oracle 실행 권한을 얻을 수 없고 모든 실행이 ValidatedPlan을 거쳐야 한다.
3 → 4단계 하나의 요청이 동일 release로 처리되고 version/hash mismatch가 fail-closed여야 한다.
4 → 5단계 Dense 호출·latency·abstain·오류와 금지 질문 무호출을 민감정보 없이 측정할 수 있어야 한다.
5 → 6단계 Schema Dense가 Registry 밖 field를 반환하지 않고 low-margin에서 실행 대신 abstain해야 한다.
6 → 7단계 Fake HCLX의 malformed·field·숫자·operator·direction 공격과 장애 fallback 테스트를 모두 통과해야 한다.
7 → Canary 실제 HCLX blind 평가, outbound 보안, latency·token budget, Fast Path 무회귀를 모두 충족해야 한다.
8 → 운영 배포 동시성·overload·timeout·provider 장애·DB mismatch fault injection 결과가 정해진 정책과 일치해야 한다.
9 → 실서비스 인증·권한·HA·DR·감사·rollback과 Product Dense 후보 범위 제한이 실제 환경에서 검증돼야 한다.

7. 자주 나오는 용어

SafetyEnvelope
탈옥·범위 밖·거래·전망 등 실행하면 안 되는 질문을 첫 단계에서 차단하는 고정 방어막.
Ontology
금융상품의 업무 개념과 데이터 field의 의미·관계를 정의한 사전.
Lexical
문자열·키워드·alias를 이용해 질문 표현과 field를 연결하는 결정론적 방법.
Dense Retrieval
Embedding으로 문장의 의미를 벡터화해 의미가 가까운 field·문서·상품을 찾는 검색.
Embedding
텍스트 의미를 유사도 계산이 가능한 숫자 배열로 바꾼 표현.
Schema Dense
사용자의 새로운 표현이 어떤 데이터 field를 뜻하는지 후보를 찾는 Dense 검색.
Product Dense
SQL로 제한된 실제 상품 중 자연어 의미와 가까운 product ID 후보를 찾는 Dense 검색.
QueryPlan
질문의 상품군·필터·정렬·비교·집계 조건을 허용된 형식으로 구조화한 계획.
ValidatedPlan
서버 검증을 모두 통과해 Oracle 실행 권한을 받은 QueryPlan과 검증 영수증.
Oracle
ValidatedPlan을 read-only SQL과 Python으로 실행해 상품과 수치를 결정하는 실행기.
Verifier
상품 ID·필터·정렬·수치·근거를 원천 데이터와 독립적으로 다시 확인하는 검증기.
BM25
문서나 상품 설명에서 검색어의 중요도를 계산하는 키워드 검색 방식.
Re-ranker
이미 찾은 소수 후보를 더 비싼 모델로 다시 비교해 순서를 정밀하게 조정하는 단계.
Vector DB
대규모 Embedding 벡터를 저장하고 ANN 등으로 빠르게 검색하는 전용 저장소.
Shadow
새 기능 결과를 기록·평가만 하고 실제 응답이나 SQL 실행에는 반영하지 않는 상태.
Canary
검증된 일부 질문이나 소수 트래픽에만 새 기능을 적용해 위험을 제한하는 단계.
Circuit Breaker
외부 Provider 오류가 반복되면 호출을 잠시 차단해 전체 서비스 장애를 막는 장치.
ExecutionAdapter
동일한 ValidatedPlan을 SQLite·PostgreSQL·사내 API 등 서로 다른 저장소에 연결하는 교체 지점.

문서 상단에 반드시 표시

  • 기준일·대상 branch 또는 release
  • 완료 보고서인지 구현 계획인지
  • 실제 배포·운영 반영 여부

  1. 목적과 쉬운 설명
  2. 핵심 구현·영향 범위
  3. 완료·활성화 기준
  4. 단계 하단 3줄 요약

주장과 상태 표기

  • 검증 완료 실제 코드·테스트 근거가 있는 상태
  • Shadow 평가만 하며 응답에는 영향이 없는 상태
  • 계획 구현 또는 독립 검증이 남은 상태

  • 큰 변경마다 날짜가 포함된 새 snapshot HTML을 만들고 이전 문서를 보존한다.
