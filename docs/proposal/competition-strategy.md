# 예선 1등을 목표로 한 실행 전략

상태: 실행 중 · 내부 우선순위 정본

기준일: 2026-08-08

이 문서는 1등을 보장하는 문서가 아님
통제할 수 없는 경쟁팀의 수준을 추측하는 대신, 공식 배점에서 잃을 수 있는 점수를
줄이고 우리만의 검증 근거를 만드는 실행 기준임

## 0. 결론

현재 가장 중요한 일은 화면을 만드는 것이 아니라 **처음 보는 자연어 질문을 정확한
검색·비교·계산 작업으로 바꾸는 능력**을 높이는 것임

공식 예선 배점은 소스코드 20%·기술제안서 40%·평가 API 답변 40%이며, 예정된
30문항에는 답할 수 없는 질문 5개와 응답 시간 평가가 포함됨

따라서 다음 세 가지를 동시에 준비

1. 비공개 질문에서 상품명·수치·근거를 정확하게 맞히는 실행 엔진
2. 모르는 질문에는 추측하지 않는 안전장치와 60초 안의 안정적인 API
3. 무엇을 왜 만들었고 실제로 얼마나 좋아졌는지를 재현 가능한 실험으로 설명하는 제안서

로컬 Qwen은 공식 답변 모델이 아니라 이 세 가지를 싸게 반복 시험하는 개발 도구로 사용
최종 평가 경로의 생성 모델은 공식 규칙에 맞춰 HyperCLOVA X로 교체

## 1. 배점에 맞춘 투자 순서

| 우선순위 | 공식 배점과 연결 | 지금 할 일 | 완료 판단 |
| --- | --- | --- | --- |
| P0 | API 답변 40% | 질문 이해, 정확한 검색·계산, 근거 검증, 답변 불가 처리 | 미사용 질문에서 상품·수치·근거 strict 개선, 치명적 퇴행 없음 |
| P0 | 기술제안서 40% | 문제·방법·실험·한계를 하나의 증거 흐름으로 연결 | 모든 정량 주장이 baseline·commit·재현 명령에 연결 |

| P2 | 시연·확장성 | 성능 동결 후 핵심 흐름을 보여주는 얇은 화면 | 대표 질문·근거·검증 상태를 설명 가능한 수준으로 표시 |

UI는 예선 API 답변 정확도를 높이지 않으므로 P0 성능 실험과 HyperCLOVA X 연결 뒤에
진행

## 2. Qwen으로 끝까지 할 수 있는 일

### 2.1 질문 이해 압박 시험

- registry와 실제 데이터에서 실행 가능한 정답 QueryPlan을 먼저 생성
- 각 계획을 Qwen이 정중체·대화체·검색창형의 서로 다른 세 문장으로 표현
- 필드·값·부등호·정렬 방향·개수가 보존됐는지 코드로 검사
- 통과한 질문만 Agent에 넣고 Router·계획·검색·근거 중 처음 실패한 위치를 기록
- 생성 실패나 의미가 바뀐 질문도 숨기지 않고 전체 요청 분모에 포함

이 실험은 299개 실행 가능한 계획에서 최대 897개 질문을 만들며, 기존 개발자가 직접
작성한 몇십 문항보다 훨씬 넓은 표현 공백을 찾기 위한 것임

### 2.2 모델 역할 분리 실험

같은 질문을 다음 네 구성으로 비교

| 구성 | 확인할 내용 |
| --- | --- |
| 모델 없음 | 현재 규칙형 질문 이해와 결정론적 답변의 기준선 |
| Qwen 계획만 | 자연어를 QueryPlan으로 바꾸는 데 모델이 실제로 기여하는 정도 |
| Qwen 답변만 | 같은 검색 결과를 더 읽기 쉽게 설명하는 효과와 fallback 비용 |
| Qwen 계획+답변 | 로컬 개발 환경에서 가능한 전체 경로의 상한과 지연 |

전체 정확도만 비교하지 않고 다음을 함께 기록

- 정답 QueryPlan 일치율
- 상품 ID·수치·순위·기준일·출처 근거 일치율
- 기존 실패를 살린 문항 수와 기존 정답을 망가뜨린 문항 수
- 생성 거절·모델 오류·검증 실패·결정론적 fallback 수
- 호출 횟수와 p50·p95·최대 응답 시간
- 같은 질문의 paired 차이와 95% 신뢰구간

### 2.3 공격·변형 시험

- 조건 순서 변경, 띄어쓰기·줄임말·오타, 부정 표현, 경계값과 동률
- 존재하지만 질문에는 없는 상품 ID를 모델이 끼워 넣는 공격
- 질문의 조건을 누락하거나 반대로 바꾸는 계획
- 데이터에 없는 전망·추천·실시간 값 요청
- provider timeout·잘못된 JSON·DB 일부 장애·동시 요청
- 동일 질문 반복 시 결과 의미가 바뀌지 않는지 확인

Qwen이 틀리는 것은 실패가 아니라 제출 전에 약점을 발견하는 데이터임
단, 같은 시험지를 보며 고친 결과는 개발 회귀로만 기록하고 독립 blind라고 부르지 않음

## 3. 기술을 추가하는 판단 기준

GraphDB·Vector DB·embedding·re-ranker처럼 이름이 돋보이는 기술도 다음 조건을 모두
만족하지 않으면 넣지 않음

1. 공식 사용 규칙과 데이터 사용 범위가 확인됨
2. 현재 SQL·BM25 기준선과 동일한 미사용 질문에서 비교함
3. 상품·수치·근거 strict 정확도나 사람 평가가 실제로 개선됨
4. 기존에 맞던 중요한 질문을 망가뜨리지 않음
5. 60초 시간 예산과 서버 비용을 감당함
6. 답변의 출처와 기준일을 끝까지 보존함

기술 개수보다 중요한 것은 **왜 이 기술이 이 질문을 더 정확하게 만들었는지 증명하는
ablation**임. ablation은 구성요소를 하나씩 켜고 꺼 효과를 비교하는 실험을 뜻함

## 4. 채택·보류·중단 기준

### 채택

- 같은 미사용 질문에서 strict 정확도 개선
- 기존 정답의 치명적 퇴행 0건 또는 원인을 설명하고 차단 가능
- 답변 불가 질문 안전 처리 유지
- p95가 공식 60초 권장 시간을 충분히 만족
- 결과를 baseline과 재현 명령으로 보존 가능

### 보류

- 평균은 좋아졌지만 특정 상품군·필드가 크게 악화
- 기계 검사는 통과했으나 금융 담당자의 의미 검수가 남음
- Qwen에서는 효과가 있지만 HyperCLOVA X에서 재검증하지 않음
- 외부 문서의 출처·사용 조건이 확정되지 않음

### 중단

- 설명만 자연스러워지고 상품·수치·근거 정확도는 개선되지 않음
- 검증기를 우회하거나 출처 없는 값을 만들 가능성이 증가
- 지연·운영 복잡도에 비해 미사용 질문 개선이 없음
- 제안서용 장식 외에 측정 가능한 효용이 없음

## 5. 실제 실행 순서

1. 현재 Git commit과 299개 정답 계획을 잠금
2. Qwen 10개 계획·30개 질문 pilot 실행
3. 생성 질문의 의미 보존 실패와 모델 오류를 사람이 표본 검토
4. 문제가 없으면 299개 계획·최대 897개 질문 전체 생성
5. 모델 없음과 Qwen 계획 경로를 같은 질문에서 비교
6. 개선이 큰 필드·연산자와 퇴행 사례를 함께 확인
7. 공통 원인 하나씩 수정하고 전체 공개 회귀를 다시 실행
8. 수정에 쓰지 않은 외부 blind 질문을 금융 도메인 담당자가 봉인하고 최초 1회 실행
9. 최소 2명이 답변의 정확성·근거성·이해 용이성을 독립 평가
10. HyperCLOVA X를 같은 동결 질문에 연결해 Qwen과 역할별 차이를 측정
11. 실제 Docker `GET /answer`의 60초·동시성·장애 복구를 검증
12. 성능과 근거가 동결된 뒤 기술제안서 표·그림과 얇은 시연 화면 제작

## 6. 사람이 해야 하는 일

자동화만으로는 1등에 필요한 마지막 증거를 만들 수 없음

| 담당 | 필요한 일 | 이유 |
| --- | --- | --- |
| AI Agent | 실험 실행, 실패 원인 수정, baseline·재현 명령 관리 | 모델과 코드의 실제 개선을 증명 |
| Financial Domain | 개발자가 보지 않은 질문·정답 작성, 금융 의미와 결측 검수 | self-authored 시험의 착시 방지 |
| Frontend & Backend | 공개 API 배포·운영, 최종 대표 화면 | 평가 기간의 안정성과 전달력 확보 |
| 팀 전체 | 제안서 주장·한계·사용자 가치 교차 검토 | 구현 사실과 과장 표현의 불일치 방지 |

AI 담당자가 지금 직접 할 수 있는 가장 가치 있는 일은 다음 순서임

1. Qwen 대규모 질문 캠페인 실행과 실패 지도 작성
2. 가장 많은 문항을 살리는 질문 이해 공통 로직 개선
3. 답변 불가·근거·경계값 공격 시험 확대
4. 역할별 ablation과 지연·오류 통계 동결
5. 외부 blind를 받는 즉시 한 번만 실행할 수 있는 상태 유지
6. HyperCLOVA X가 열리면 같은 시험으로 교체 비용과 성능 차이 측정

## 7. 최종적으로 심사위원에게 보여줄 증거

- 네 상품군 원천 데이터의 품질 문제와 처리 원칙
- 자연어 질문이 QueryPlan·SQL·검증 근거·답변으로 이어지는 추적 가능한 흐름
- 모델 없음·계획 모델·답변 모델의 역할별 성능 비교
- 개선 전후의 rescued·regressed 문항과 통계적 불확실성
- 답변 불가 5개 유형과 공격 질문에서 추측을 차단한 결과
- 실제 Docker API의 재현 명령·응답 시간·장애 fallback
- 외부 blind와 사람 평가 결과 및 실패 사례를 숨기지 않은 분석
- 아직 지원하지 않는 범위와 Graph·Vector·문서 RAG의 조건부 확장 계획

압도적인 결과물은 기술 이름이 많은 결과물이 아니라, **정답률·근거·안전·속도와
재현성이 한 흐름으로 증명되는 결과물**을 의미함
