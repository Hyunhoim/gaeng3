## 3. 공식 평가 API 계약

### 요청

```http
GET /answer?question_id=Q-001&question={URL-encoded-question}
```

| query parameter | 타입 | 필수 | 처리 원칙 |
| --- | --- | --- | --- |
| `question_id` | string | 필수 | 응답에 같은 값 반환 |
| `question` | string | 필수 | URL decoding 후 처리하고 응답에 원문 반환 |

### 응답

```json
{
  "question_id": "Q-001",
  "question": "질문 원문",
  "retrieved_context": "근거를 문자열로 직렬화한 값",
  "think_trace": "검증 가능한 실행 기록을 문자열로 직렬화한 값",
  "answer": "최종 답변"
}
```

- 다섯 필드는 모두 필수 문자열
- 성공·미검색·역질문·미지원·내부 실패 모두 같은 스키마와 HTTP 200으로 반환
- 정의되지 않은 추가 query parameter가 들어와도 HTTP 500을 내지 않음
- 내부 Frontend·Backend용 상세 DTO는 유지하고 공식 평가용 adapter를 별도로 추가
- 공식 adapter는 내부 DTO의 추가 필드를 그대로 노출하지 않음

### `think_trace` 팀 설계

숨은 사고과정이나 자유로운 장문 추론을 노출하지 않고 다음 실행 사실만 기록

- 판별한 intent와 상품군
- 선택한 도구와 적용한 필터·정렬·집계
- 검색 후보와 반환 개수
- Result Verifier와 Answer Verifier 결과
- 근거·기준일 상태
- fallback 사용 여부와 안전한 사유 코드

이 방식이 공식 채점 의도에 충분한지는 서면 확인이 필요하지만, 현재 구현은 보안과
재현성을 위해 구조화 실행 기록을 기준으로 함

## 4. Ontology 제출 기준

현장 화면에는 다음 파일이 도메인별 신규 필수 제출물로 표시됨

```text
ontology/
├── common.ttl
├── bond_kr.ttl
├── etf_kr.ttl
├── etf_gl.ttl
└── fund_pub.ttl
```

- Turtle 문법으로 작성
- 현재 `field_registry.yaml`의 의미·자료형·단위·관계를 정본으로 사용
- Ontology와 registry 불일치를 자동 검사
- 구두 메모의 “꼭 TTL일 필요는 없음”은 서면 화면과 충돌하므로 공식 답변 전까지
  `.ttl` 제출을 안전 기준으로 채택
- GraphDB나 Vector DB를 형식적으로 추가하지 않고, 현재 SQL·BM25 기준선보다 실제
  품질이 좋아지는 경우에만 실험 후 채택

## 5. HyperCLOVA X와 크레딧 상태

### 확인된 크레딧 안내

- 팀당 20만 원
- 대표자 신청 후 승인까지 최대 2영업일
- 승인 후 콘솔에서 쿠폰을 직접 등록
- 만료일 2026-09-30
- 초과 비용과 지원 대상이 아닌 서비스 비용은 팀 부담

### 아직 확인할 내용

- 크레딧 승인·쿠폰 등록 완료 여부
- HyperCLOVA X가 해당 크레딧의 지원 서비스인지
- 공모전에서 허용되는 정확한 HyperCLOVA X 모델 ID
- 실제 endpoint, 인증 header, request·response body
- Structured Outputs 또는 JSON Schema 지원 범위
- timeout, QPS, 동시 요청, 입력 길이, retry 규칙

크레딧과 실제 API 계약을 확보하기 전에는 endpoint·header·model ID를 추측해 구현하지
않음. 현재 fake transport 계약과 개발 전용 로컬 Qwen 경로를 유지

## 8. 구현 순서

### P0 — 공식 제출 계약

1. 공식 응답 5필드 Pydantic DTO 추가
2. `GET /answer` query parameter adapter 추가
3. 성공·미검색·역질문·미지원·오류의 HTTP 200 계약 테스트
4. 내부 전체 처리 시간을 60초보다 짧게 제한하고 timeout fallback 검증
5. `ontology/`의 Turtle 파일 5개 작성
6. Ontology 문법과 field registry 정합성 자동 검사

1~3은 2026-08-07 완료. Agent Core 346건과 Backend 26건 테스트가 통과했으며,
Docker의 실제 공식 GET smoke는 전체 재검증 단계에서 확인

### P1 — 크레딧 없이 계속할 내부 검증

1. 로컬 Qwen 서버·Docker Backend 전체 경로 smoke 재현
2. `internal-red-team-v1`과 공개 회귀 세트 재실행
3. 공식 30문항 구성을 참고한 새 질문 분포 설계
4. 답할 수 없는 질문을 최소 5개 포함해 안전 처리·200 스키마 검증
5. 질문별 총 latency와 QueryPlan·답변 생성·Verifier 시간을 분리 기록
6. 결정론적 답변과 로컬 Qwen 답변의 사람 평가 표본 준비

## 9. 완료 기준

- 공식 `GET /answer`가 모든 결과에서 다섯 문자열 필드와 HTTP 200을 반환
- 정의되지 않은 query parameter와 provider·dataset 장애가 HTTP 500을 노출하지 않음
- Ontology 5개가 Turtle parser와 field registry 정합성 검사를 통과
- 로컬 Qwen을 끈 기본 CI·Docker·결정론적 fallback 경로가 계속 통과
- 로컬 Qwen 시험 결과와 공식 HyperCLOVA X 결과가 문서·artifact에서 명확히 분리
- 제출 후보에 로컬 모델 weight·cache·provider·설정·스크립트·credential이 없음
- 기술제안서의 모든 완료 주장과 수치가 코드·baseline·근거 맵에 연결

설명회에서 답을 얻지 못한 항목은 추측하지 않고 기존 보수적 정책을 유지
