# 공식 자료 대비 아키텍처 격차 분석

작성일: 2026-08-31
기준 commit: `24cfb2e`
분석 대상: `0. Official Materials`의 과제 소개·과제 설명·기술 세션 자료와 Discord 공지·기술 질문답변

> 공식 자료 원문은 대회 외 사용이 금지되어 있다. 이 문서는 요구사항을 우리 구현과
> 대조하기 위한 내부 작업 문서이며 원문을 옮기지 않는다.

## 0. 결론

주최 측이 기대하는 아키텍처는 **Define(Ontology) → Connect(Knowledge Graph) →
Retrieve(Federated Query) → Reason(LLM)**이며, 우리 구조는 이 형태를 이미 갖추고 있다.
질문 분해와 라우팅도 실제로 동작한다.

**약점은 구조가 아니라 근거 데이터의 폭이다.** 기업 단위 관계(자회사·구성종목)를
검증된 형태로 확보하지 못해, 난이도 [상]에 해당하는 질문에서 `확인할 수 없음`으로
끝난다. 답변 불가 질의는 정확히 처리하므로 감점 위험은 낮다.

## 2. 요구 아키텍처 대비 현재 위치

| 공식 자료가 요구하는 층 | 우리 구현 | 판정 |
| --- | --- | --- |
| Ontology (TBox, 런타임 통제) | `field_registry.yaml`에서 Turtle 5종을 생성하고 동일성을 검사. registry가 실행 권한·필드·연산자를 확정 | **강함** |
| Knowledge Graph (ABox) | 승인 DB 기반 관계 색인 37,793개. 자산유형·투자지역·발행사 중심 | **약함** |
| RDB (숫자·필터) | 네 상품군 SQLite, 결정론적 Oracle, 0·결측 제외 | **강함** |
| Vector (의미 검색) | Schema Dense가 field 후보만 제안. 상품 Dense는 최종 Release에서 OFF | 보통 |
| Federated Query (분해·라우팅·통합) | 질문을 capability 단위로 분해하고 상품군·정렬까지 계획 | **강함** |
| Answer Generator (근거·환각 방지) | Verifier + Answer Verifier + 결정론적 fallback | **강함** |

### 2.1 질문 분해는 실제로 동작한다

예시 5번을 보낸 응답의 실행 기록에는 세 요구사항이 분리되어 있었다.

```
corporate_subsidiary   subsidiary_of   "에코프로의 자회사"
portfolio_holdings     holds_company   "편입한"
product_risk_factors   has_risk_factor "위험요인"
ranking: aum desc limit 1
```

주최 측이 설명한 Decomposition → Routing → Mapping이 그대로 수행됐다.
실행이 멈춘 지점은 `temporal_relation_verifier`이며 근거 검증 단계다.

### 2.2 승인 capability는 공식 예시와 1:1로 대응한다

`approved_knowledge_coverage_manifest.json`의 다섯 capability는 공식 예시 질문의
성격과 정확히 겹친다.

| capability | 대응 예시 | 실측 |
| --- | --- | --- |
| `fund_structure_strategy_trend` | 펀드 구조·투자전략 동향 | 부분 |
| `sector_theme_history` | 테마 연결 이력 | **정상** |
| `portfolio_holdings` | 구성종목 편입 | **실패** |
| `corporate_subsidiary` | 자회사 | **실패** |
| `product_risk_factors` | 위험요인 | **실패** |

다섯 개 모두 `runtime_execution_enabled: true`다. 즉 배선은 열려 있고
실행 결과만 갈린다.

## 3. 확인된 약점

### 3.1 기업 단위 관계 근거가 부족하다 — 최우선

`portfolio_holdings`와 `corporate_subsidiary`가 실패하는 이유는 계획이 아니라
검증된 관계 사실이 없기 때문이다. 승인 관계 색인의 엔터티 2,015개는 전부
자산유형·투자지역·발행사이고 개별 기업이 없다. 기업 관계는 release 시 주입하는
`external-temporal-relations.json` 번들에 의존하는데, 실측 결과 예시 질문이 요구한
관계가 그 번들에 없다.

주최 측 기술 세션은 이 지점을 직접 지목했다. RDB에 테마 컬럼이 없어 0건이던 질의가
Graph로는 36건이 되었다는 자체 실험을 공개했고, 단일 검색기의 천장이 약 66%이며
RDB와 Graph 결합이 가장 안정적이라고 밝혔다.

**보완 방향.** 승인 출처 14곳에서 기업 관계를 수집해 번들을 넓힌다. 출처·게시일·
수집일·본문 해시를 보존하고 2026-08-24 상한을 지키는 현재 계약을 그대로 사용한다.
이 작업은 실제 수집이 필요하므로 NCP 자격증명과 금융 도메인 검수가 선행되어야 한다.

### 3.2 외부 근거가 붙으면 응답이 느려진다

예시 4번이 33.3초, 3번이 19.5초였다. 공식 자료는 문항당 60초 이내를 권장하고
응답 소요 시간을 평가 항목으로 명시한다. Discord의 300초는 상한이지 목표가 아니다.

현재 연구실 측정 p95는 7.038초지만 그것은 외부 탐색이 적은 문항이 다수인 분포다.
난이도 [상] 문항이 외부 관계를 요구한다면 실제 분포는 더 느려진다.

**보완 방향.** capability별 시간 예산과 공식 문서 cache 확대. 2026-08-29 보고서도
같은 결론을 냈다.

### 3.3 제안서가 우리 강점을 주장하지 않는다

주최 측은 온톨로지를 프롬프트 설명으로 주입하면 +2.4pp, 런타임 식별에 사용하면
+20pp라는 자체 실험을 공개했다. 우리는 `field_registry.yaml`이 Turtle 5종의 정본이며
동시에 실행 권한·필드·연산자·정렬을 확정하는 런타임 통제 계층이다. 즉 그들이
효과가 크다고 밝힌 방식을 이미 쓰고 있다.

그런데 현재 기술 제안서에는 `런타임 온톨로지`라는 주장이 없다.

또한 공식 권장 목차는 제안 방법을 세 질문에 답하는 형태로 요구한다.

1. 어떤 특화 데이터를 어떻게 수집·정제했는가
2. 어떤 온톨로지 엔지니어링을 적용했는가
3. 어떤 검색 방법론을 선택했고 왜 그렇게 설계했는가

1번은 2026-08-31에 추가했다. 2번과 3번은 아직 그 형태로 서술되어 있지 않다.

### 3.4 제출 항목 하나가 준비되지 않았다

공식 제출물은 소스코드·기술 제안서·평가용 API 서버 정보 3종이다. 세 번째는
`End-point URL + API 명세서(요청/응답 JSON 스키마)`를 필수로 명시한다.
현재 저장소에 제출용 API 명세서 문서가 없다.
