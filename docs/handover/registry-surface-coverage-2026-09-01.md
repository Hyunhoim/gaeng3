# registry 표면형 커버리지 (정렬·필터)

작성일: 2026-09-01

## 1. 무엇을 쟀는가

`field_registry.yaml`은 이 시스템의 런타임 통제 계층이다. 어떤 field가 정렬
가능한지, 어떤 표현이 그 field를 가리키는지를 여기서 확정한다. 그렇다면
registry가 `label`이나 `aliases`로 선언한 표현은 **반드시 답이 되어야 한다.**

선언된 표면형으로 질문을 만들어 실제로 그 field로 정렬되는지 확인했다.

```
"{표면형}이 높은 {상품군} 3개"
```

대상은 숫자형이면서 정렬 가능한 field 46개, 표면형 140건이다.

## 2. 결과

| | 실패 | 비율 |
| --- | ---: | ---: |
| 착수 전 | 36건 | 25.7% |
| 현재 | 3건 | 2.1% |

멀티턴이 금지되어 있으므로 되물음은 곧 0점이다. 실패 유형은 두 가지였다.

- **되물음 29건** — 표현을 못 알아들어 조건을 다시 묻는다
- **오매핑 4건** — 다른 field로 정렬해 **틀린 답**을 낸다

오매핑이 더 위험하다. 예를 들어 `120거래일 연환산 변동성`이 `20거래일 변동성`으로
매핑되어 다른 기간의 값을 답했다.

## 3. 원인

registry는 별칭을 선언하지만, 정렬 인식은 **손으로 쓴 정규식**에만 의존했다.

| 목록 | 규모 |
| --- | --- |
| `SEMANTIC_ALIAS_RULES` | 규칙 25개, 덮는 field 18개 |
| `linker.explicit_rank_patterns` | 상품군별 하드코딩 |
| `semantic_gate._DIRECTION_METRIC_PATTERN` | 별도 손글씨 목록 |
| `semantic_gate._EXPLICIT_RETURN` | 또 다른 손글씨 목록 |

같은 정보가 네 곳에 따로 적혀 있고 registry와 동기화되지 않았다. registry에
별칭을 추가해도 아무 일도 일어나지 않는 상태였다.

## 4. 조치

### 4.1 registry에서 정렬 패턴을 생성한다

`linker.registry_rank_patterns(family)`가 registry의 숫자형 정렬 가능 field
전부에 대해 `label`과 `aliases`로 패턴을 만든다. 손으로 쓴 규칙 뒤에 놓아
추가 맥락을 담은 기존 규칙이 우선권을 유지한다.

이제 registry에 별칭을 추가하면 그것만으로 동작한다.

### 4.2 짧은 표면형이 긴 것 안에서 매칭되지 않게 한다

생성 패턴에 왼쪽 경계 `(?<![0-9A-Za-z가-힣])`를 넣었다.

```
120거래일 변동성  →  20거래일 변동성 으로 매칭되던 것을 차단
총발행금액        →  발행금액       으로 매칭되던 것을 차단
```

`순자산가치`는 손으로 쓴 `aum` 패턴이 `순자산`으로 먼저 잡았다. 해당 패턴에
`순자산(?!가치)`를 넣어 분리했다.

### 4.3 게이트가 registry를 근거로 인정하게 한다

의미 커버리지 게이트는 방향어(`높은`)만 남으면 모호하다고 판정한다. registry가
선언한 표면형이 앞에 있으면 근거로 인정하도록 세 지점을 고쳤다.

- `_direction_has_metric` — 앞 문맥이 registry 표면형이면 통과
- `_metric_has_explicit_mapping` — `가격 괴리율`처럼 모호한 토큰으로 시작하는
  표면형을 인정하되, `가격`만 있으면 계속 모호로 남긴다
- `_schema_link_gap_matches` — `2Y 수익률`이 `수익률`로 잘려 들어오는 것을
  앞 문맥과 함께 다시 읽는다
- `_DIRECTION_TERM` 루프 — `최신 분배율`처럼 방향어로 시작하는 표면형은 건너뛴다

### 4.4 기간 축약 표기를 맞춘다

`_EXPLICIT_RETURN`·`_EXPLICIT_PERIOD_RETURN`·`_DIRECTION_METRIC_PATTERN`·
`_NUMERIC_SORT_METRIC_PATTERN`에 `18M`·`2Y`·`3Y`·`5Y`를 추가했다. `1D`·`1W`·
`1M`·`1Y`·`YTD`는 이미 있었는데 이 넷만 빠져 있었다. `민평 산출 수익률`도 함께
넣었다.

## 5. fail-closed는 유지된다

표현을 넓히면서 근거 없는 실행이 새지 않는지 함께 고정했다.

```
가격이 높은 국내 ETF     계속 되물음  (registry 표면형이 아님)
비용이 낮은 국내 ETF     계속 되물음
```

## 6. 남은 3건

```
국내 채권 구성비가 높은 공모펀드
해외 채권 구성비가 높은 공모펀드
펀드 기준가가 높은 해외 ETF
```

표면형 안에 다른 상품군 이름이 들어 있어 한 문장이 두 상품군을 가리킨다.
컴파일러가 거절하는 것이 맞는 동작이므로 고치지 않았다. 테스트에서 명시적으로
제외하고 이유를 적었다.

## 7. 회귀 고정

`tests/test_registry_surface_coverage.py`가 registry를 읽어 표면형마다 테스트를
만든다. 별칭을 추가했는데 동작하지 않으면 그 자리에서 실패한다. 경계 충돌 3건과
모호 표현 2건도 함께 고정했다.


## 8. 필터 조건 표현 (2026-09-01 추가)

정렬과 같은 방법을 임계값 조건에 적용했다. `gte`/`lte`를 허용하는 숫자 field
46개의 표면형으로 `"{표면형} {값} 이상인 {상품군} 3개"` 형태를 만들어 실제로
그 제약이 걸리는지 확인했다.

| | 실패 | 비율 |
| --- | ---: | ---: |
| 착수 전 | 40건 | 14.3% |
| 현재 | 8건 | 2.9% |

### 왜 정렬보다 위험한가

정렬 실패는 되물음으로 끝나 0점이다. 필터 실패는 다르다. **질문은 실행되고
조건만 조용히 사라진다.** `연간 수익률 0.5% 이상인 국내 ETF`가 조건 없이
아무 ETF 3개를 답한다. 채점자가 보기에 이는 틀린 답이다.

### 원인

`numeric_fields`는 상품군별로 손으로 쓴 `(field, aliases)` 목록이다. registry가
선언한 별칭 중 일부만 들어 있었다. 예를 들어 `one_year_return_pct`에는
`1년 수익률`은 있고 `연간 수익률`은 없었다.

### 조치

`registry_numeric_aliases(family)`가 registry에서 임계값 별칭을 만들고, 기존
목록과 **field 단위로 병합**한다. 처음에는 이미 있는 field를 건너뛰게 했는데,
그러면 그 field의 빠진 별칭이 그대로 남는다. 빠진 별칭이 정확히 문제였으므로
병합이 맞다.

곁들여 두 가지를 고쳤다.

- `_COMPARATIVE_CUE`의 `민감`이 `금리 민감도`라는 **field 이름**에 반응해
  정렬 의도로 오인했다. `민감(?!도)`으로 분리했다
- `금리에 더 민감한`이 인식되지 않았다. 규칙이 `금리 변화에`만 허용하고
  `금리에`를 빠뜨렸다

### 회귀가 잡아낸 것

병합 후 전체 회귀에서 `test_phase2_numeric_aliases_do_not_cross_contaminate_fields`
1건이 깨졌다. registry가 `leverage_factor`의 별칭으로 선언한 `배수`가
`분배수익률` 안에서 매칭되어, 분배수익률 질문에 레버리지 임계값이 붙었다.

정렬에서 이미 고쳤던 것과 같은 문제다. `_alias_group()`을 두어 숫자 별칭
매칭 전체에 왼쪽 경계와 긴 별칭 우선을 적용했다. `_numeric_hint`,
`_excluded_numeric_hint`, `_negated_comparison_span`, `_date_hint`, 그리고
`N등/N위` 패턴이 모두 같은 헬퍼를 쓴다.

기존 테스트가 이 오염을 이미 감시하고 있었다는 점이 중요하다. registry에서
별칭을 자동으로 끌어오면 경계 처리가 필수라는 뜻이다.

### 남은 8건

`국내 채권 구성비`·`해외 채권 구성비`·`펀드 기준가` 3종의 이상/이하 각 1건이다.
정렬과 같은 이유로 상품군이 섞이는 경우이며 거절이 맞는 동작이다.
