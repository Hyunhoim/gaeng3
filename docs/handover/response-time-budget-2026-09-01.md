# 응답 시간 예산 분석

작성일: 2026-09-01
대상 commit: `a3d2f65` (PR #51·#52·#53 병합본 + 띄어쓰기 수정)

## 1. 왜 보는가

공식 자료는 문항당 **60초 이내**를 권장하고 응답 소요 시간을 평가 항목으로
명시한다. Discord에 공지된 300초는 상한이지 목표가 아니다.

2026-08-31 공식 예시 문항 실측에서 외부 근거가 붙는 두 문항이 각각 **19.5초**와
**33.3초**였다. 33.3초는 권장선의 절반을 넘는다.

## 2. 측정 결과

### 2.1 결정론 경로는 병목이 아니다

로컬 개발 컨테이너(HCLX 자격증명 없음)에 12개 질의를 보냈다.

| 질의 유형 | 소요 |
| --- | --- |
| 국내 ETF 순자산 정렬 5개 | 0.660초 |
| 해외 ETF 순자산 정렬 5개 | 0.315초 |
| 국내채권 잔존만기 조건 5개 | 0.856초 |
| 국내채권 표면금리 정렬 5개 | **1.588초** (최대) |
| 국내 ETN 거래대금 정렬 5개 | 0.151초 |
| 차단·clarify 응답 | 0.017 ~ 0.045초 |

Router → Linker → Compiler → Oracle → Verifier → Renderer 전 구간이
**2초 미만**이다. 19.5초·33.3초의 원인이 아니다.

### 2.2 승인 출처 1회 fetch도 병목이 아니다

승인 출처 24곳의 hostname에 각 1회 GET을 보내 왕복 시간을 쟀다.

```
표본 21건   중앙값 0.16초   평균 0.36초   최대 2.23초
```

`max_fetches` 상한인 32회를 모두 써도 산술적으로 12초 안팎이다.

### 2.3 그렇다면 남은 시간은 어디에 있는가

구간별 상한을 코드에서 모으면 다음과 같다.

| 구간 | 설정 위치 | 상한 |
| --- | --- | --- |
| 전체 응답 | `OFFICIAL_ANSWER_TIMEOUT_SECONDS` | **270초** |
| HCLX 1회 호출 | `HCX_TIMEOUT_SECONDS` | **45초** |
| 외부 탐색 전체 | `ExternalSearchBudget.deadline_ms` | **60초** |
| 개별 fetch | `official_acquisition.py:327` | **30초** |
| 검색 질의 수 | `max_search_queries` | 40회 |
| fetch 수 | `max_fetches` | 32회 |

**어느 값도 60초 권장선에서 역산되지 않았다.** 각각 독립적으로 정해진 상한이라,
단순 합산 최악값은 150초를 넘는다.

측정된 결정론 경로 2초와 fetch 12초를 빼면, 33.3초의 대부분은 **HCLX 생성 호출과
검색 질의 왕복**에 있다고 보는 것이 타당하다. 다만 이는 추정이며 확정하려면
구간별 `duration_ms`가 필요하다 (아래 4절).

## 3. 구조적 문제 두 가지

### 3.1 외부 탐색 예산이 권장선 전체와 같다

`ExternalSearchPlanCompiler.compile()`은 `budget` 인자를 받지만
`routed_service.py:905`에서 인자 없이 호출된다. 따라서 항상 기본값
`deadline_ms=60_000`이 쓰인다.

외부 탐색 **한 구간**이 문항 전체 권장 시간을 다 쓸 수 있다는 뜻이다.
라우팅·HCLX·SQL·검증·렌더링은 그 위에 얹힌다.

### 3.2 응답 없는 호스트 하나가 예산의 절반을 먹는다

```python
timeout_seconds=min(30.0, max(0.1, remaining_seconds))
```

승인 출처의 실측 중앙값이 0.16초인데 상한은 30초다. 한 곳이 응답하지 않으면
60초 예산의 절반이 그 한 번에 소진된다. 2.3초 안에 응답하지 않는 공식 페이지가
그 뒤에 유용한 근거를 줄 확률은 낮다.

## 4. 확정에 필요한 것

`AuditStage`는 `request`부터 `answer`까지 18개 구간을 정의하고 각
`duration_ms`를 기록한다. 즉 **계측은 이미 되어 있다.**

19.5초·33.3초를 낸 그 실행의 audit JSONL만 있으면 구간별로 분해된다.
해당 로그는 배포 서버에 있다.

- 요청 대상: 임현호
- 필요한 것: 2026-08-31 공식 예시 3번·4번 문항 실행의 audit JSONL
- 확인할 것: `hclx`·`dense`·`execution` 구간의 `duration_ms` 비중

## 5. 제안하는 예산표

60초 권장선에서 역산한다. 관측된 실측값에 여유를 둔 값이다.

| 구간 | 현재 | 제안 | 근거 |
| --- | --- | --- | --- |
| 외부 탐색 전체 | 60초 | **25초** | fetch 실측 12초 + 여유 |
| 개별 fetch | 30초 | **10초** | 실측 최대 2.23초의 약 4.5배 |
| HCLX 1회 | 45초 | 유지 | 생성 시간은 우리가 통제하지 못함 |
| 전체 응답 | 270초 | 유지 | 상한은 상한대로 둔다 |

합계 목표: 외부 근거 문항 **45초 이내**, 결정론 문항 **5초 이내**.

### 주의

외부 탐색 예산을 줄이면 근거를 찾을 수 있었던 문항이 `CANNOT_VERIFY`로 끝날
수 있다. 그 손익은 4절의 audit 로그로 실제 소요 분포를 본 뒤에 정해야 한다.
**분포를 보기 전에 상한을 내리지 않는다.**

개별 fetch 상한 10초는 이와 성격이 다르다. 응답이 느린 호스트를 일찍 포기하는
것이지 탐색 범위를 줄이는 것이 아니므로, 근거 손실 없이 꼬리 시간만 자른다.

6초가 아니라 10초로 잡은 이유가 있다. 이 값은 socket timeout이지 다운로드 전체
시간이 아니다. 즉 조금씩이라도 내려오는 큰 PDF는 끊기지 않고, 아예 응답하지 않는
호스트만 끊긴다. 다만 fsc-policy는 HTML 한 장에 2.23초가 걸렸다. 같은 호스트의
큰 PDF는 첫 바이트까지 그보다 오래 걸릴 수 있으므로 실측 최대의 4배 이상을 둔다.

## 6. 이번에 하지 않은 것

**fetch 병렬화.** `official_acquisition.py`의 fetch 루프는 순차이고, 그 안에서
`remaining_fetches`·`remaining_bytes`·deadline을 차례로 깎는다. 병렬화하면
예산 회계와 audit 순서를 다시 설계해야 한다. 실측상 fetch는 12초 수준이라
얻는 것보다 위험이 크다. 제출 이후 과제로 남긴다.
