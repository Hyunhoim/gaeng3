2. External Blind 독립성 경계

External blind는 개발자가 결과를 미리 보고 개선하지 못하도록 질문과 정답을 독립 평가자가 보관하는 평가입니다. 정답키의 품질만큼 “누가 무엇을 언제 봤는가”가 중요합니다.

허용 정답 작성에 사용할 수 있는 것

  • 이미 고정된 질문-only JSON
  • 주최 측 제공 datarows·schema Excel
  • 데이터 추출 기준일과 대회 답변 원칙
  • 동결된 QueryPlan JSON Schema
  • 표준 field registry와 projection template
  • 정확한 승인 DB snapshot·manifest·SHA-256
  • 계약 Validator와 read-only Oracle

금지 열람하거나 실행하면 안 되는 것

  • Agent의 /answer 응답과 내부 trace
  • IntentRouter·PlanningDecision·Compiler 출력
  • BGE-M3·KURE-v1·Lexical 후보와 점수
  • HCLX·Qwen 또는 다른 LLM의 Agent 예측
  • 기존 공개 회귀 질문·정답·실패 분석
  • 질문별 현재 구현의 성공·실패 여부
  • prediction 생성 뒤 정답을 고쳐 맞추는 행위
중요: 현재 Agent의 기능 한계에 맞춰 정답을 낮추지 않습니다.

정답은 “현재 코드가 무엇을 할 수 있는가”가 아니라 “주최 측 제공 데이터와 합의된 안전 원칙상 무엇이 올바른가”로 판정합니다. 현재 기능이 실패하더라도 정답을 Agent 출력에 맞춰 바꾸지 않습니다.

5.2 InteractionIntent와 QueryPlan intent

InteractionIntent쉬운 뜻EXECUTE일 때 QueryPlan intent
search조건에 맞는 상품 찾기·정렬search
detail식별자가 명확한 상품 하나 상세 조회search
compare정확히 식별된 상품 2개의 제공 필드 비교compare
aggregate개수·합계·평균·최솟값·최댓값 집계aggregate
explain식별자가 명확한 상품의 제공 필드 설명search
clarify조건이 부족해 사용자에게 역질문없음
unsupported예측·추천·데이터 밖·비금융 요청 거절없음
DETAIL·EXPLAIN 매핑 주의

현재 동결 계약에서는 DETAIL과 EXPLAIN을 정확한 식별자 기반 search QueryPlan으로 실행합니다. 사람 Intent는 각각 detail·explain로 유지하되 expected_query_plan_intent는 search입니다.

5.3 RouteDisposition 결정표

판정사용 조건예시 유형실행 정보
execute공식 제공 데이터로 의미와 계산을 하나로 확정 가능명확한 필터·정렬·상세·비교·집계QueryPlan·gold fields·Oracle 필수
clarify복수 해석, 핵심 조건 누락, 주관어의 기준 부재“안전한”, “괜찮은”, 국내/해외 미지정모두 비움
unsupported예측·개인추천·비금융·데이터 밖 사실·권한 우회미래 수익률, 매수 지시, prompt injection모두 비움

5.4 경계 사례 판정

  • 필드 자체가 상품군 데이터에 없음: UNSUPPORTED. 예: 공모펀드에 제공되지 않은 보수로 정렬.
  • 필드는 있으나 일부 행만 값이 있음: 명확한 질문이면 EXECUTE 가능. 결측을 0으로 바꾸지 않고 정렬 시 null 정책을 명시합니다.
  • 정확한 상품 식별자가 없음: DETAIL·EXPLAIN·COMPARE를 임의 상품명 매칭으로 실행하지 않고 CLARIFY합니다.
  • “높은 수익률”처럼 기간이 빠짐: 여러 기간 필드가 있으므로 CLARIFY합니다.
  • 일반 금융 개념 설명: 승인 문서 corpus가 별도로 고정되지 않았다면 상품 데이터 밖 설명으로 UNSUPPORTED합니다.
  • 질문 속 공격 지시: 데이터 검색 조건과 무관한 시스템 지시·비밀 요구는 무시하고 UNSUPPORTED로 판정합니다.

7. EXECUTE 문항의 QueryPlan 작성

QueryPlan은 질문의 의미를 서버가 검증하고 SQL/Python으로 실행할 수 있도록 제한된 JSON으로 표현한 계획입니다. LLM의 자유문장이 아니라 자료형과 허용값이 고정된 Typed Contract(형식이 엄격한 계약)입니다.

7.1 공통 구조

{
  "schema_version": "1.0",
  "question_id": "CASE_ID_FROM_QUESTION_FILE",
  "intent": "search",
  "product_families": ["domestic_etp"],
  "constraints": [],
  "ranking": [],
  "projection": ["product_id", "product_name"],
  "limit": 5,
  "intent_payload": {
    "comparison_fields": [],
    "group_by": [],
    "aggregations": [],
    "explain_product_ids": []
  },
  "ambiguities": [],
  "unsupported_conditions": []
}
위 JSON은 구조 설명용입니다.

실제 blind case에 복사하지 않습니다. 각 질문의 family·constraint·projection·limit을 registry와 공식 데이터에 맞게 별도로 작성해야 합니다.

7.2 공통 필드 규칙

필드규칙
schema_version항상 1.0
question_id현재 case의 ID와 글자 하나까지 동일
intent현재 external blind v2 정답키에서는 search·compare·aggregate만 사용. 일반 QueryPlan enum에 explain이 있어도 이 평가에서는 사용 금지
product_familiesexternal blind 정답키에서는 예상 family 하나만 포함
constraints최대 20개. field·operator·value·unit·strength를 모두 명시
ranking최대 5개. 같은 field 중복 금지
projection1~30개. 실행·비교·근거에 필요한 selectable field만 포함
limit1~100. 질문의 명시값을 우선하고 없으면 동결 정책값 사용
intent_payloadIntent별 전용 정보. 다른 Intent용 값이 섞이면 실패
ambiguitiesEXECUTE gold에서는 빈 배열. 모호하면 plan을 만들지 않고 CLARIFY

구분허용값주의사항
operatoreq, neq, in, not_in, lt, lte, gt, gte, between, containsfield registry에 허용된 operator만 사용
unitnone, code, boolean, pct_point, source_currency_amount, source_quantity, day, year, date숫자의 의미를 임의 변환하지 않고 registry 값과 정확히 일치
strengthlocked, ask_before_relaxing, preference명시 조건은 보통 locked. 주관어를 임의 숫자로 바꾸지 않음
valueboolean·number·string 또는 허용 목록숫자를 문자열로 쓰지 않으며 날짜는 YYYY-MM-DD
  • in·not_in은 비어 있지 않은 배열이어야 합니다.
  • between은 정확히 두 값의 배열이어야 합니다.
  • contains는 문자열에만 사용합니다.
  • enum 값은 registry에 적힌 철자와 대소문자를 그대로 사용합니다.
  • 결측값을 0·false·빈 문자열로 바꿔 조건에 포함하지 않습니다.

7.4 Ranking 작성

{
  "field": "one_month_return_pct",
  "direction": "desc",
  "nulls": "last"
}
  • “높은·많은·최근”의 의미가 명확할 때만 desc를 사용합니다.
  • “낮은·적은·빠른 날짜”는 보통 asc이지만 field 의미를 확인합니다.
  • 질문에 기간이 없는데 여러 수익률 기간이 존재하면 임의 선택하지 않고 CLARIFY합니다.
  • 결측 정렬은 동결 정책을 따르며 일반 상품 순위에서는 보통 nulls: last입니다.

7.5 Intent별 작성 차이

유형필수 내용금지·주의
SEARCH필터·정렬·projection·limit, intent_payload 전부 빈 배열질문에 없는 조건 추가 금지
DETAILintent=search, product_id eq constraint, limit=1, ranking=[], intent payload 전부 빈 배열상품명 유사 매칭으로 임의 확정 금지
EXPLAINintent=search, product_id eq, limit=1, ranking=[], 요청 field를 projection에 포함, intent payload 전부 빈 배열intent=explain 사용 및 사전학습 지식 보완 금지
COMPAREintent=compare, product_id in [요청순서 ID 2개], limit=2, ranking=[], comparison_fields와 projection 포함나머지 payload는 빈 배열, 상품 순서 보존
AGGREGATEintent=aggregate, aggregations 필수, 필요 시 group_byranking 금지, projection에서 집계 field 누락 금지

aggregations의 function은 count, min, max, avg, sum 중 registry가 허용하는 것만 사용합니다.

8. gold_schema_field_ids 고르기

gold_schema_field_ids는 Dense Schema Linker가 질문에서 찾아야 하는 “의미 핵심 field 정답”입니다. QueryPlan의 모든 projection을 복사하는 목록이 아닙니다.

포함

  • constraint에 쓰인 field
  • ranking에 쓰인 field
  • comparison_fields
  • aggregation field와 group_by
  • DETAIL·EXPLAIN·COMPARE의 명시적 식별자 field
  • 질문이 직접 요청한 출력 field

제외

  • 화면 표시를 위해 자동 추가된 상품명
  • 기본 근거용 기준일·원천파일 field
  • 질문에서 요구하지 않은 편의 projection
  • Agent가 우연히 후보로 낸 field
  • 해당 family에 속하지 않는 field
  • CLARIFY·UNSUPPORTED의 모든 field
최대 10개·중복 금지

EXECUTE는 1개 이상, 최대 10개의 고유한 canonical field ID가 필요합니다. 각 field는 예상 상품군에 실제로 등록되어 있어야 합니다.

8.1 선택 절차

  1. 질문을 “대상 상품군 / 필터 / 정렬 / 비교 / 집계 / 식별자 / 직접 요청 field”로 분해합니다.
  2. 먼저 한글 의미 항목을 작성합니다.
  3. field_registry.yaml에서 해당 family의 canonical ID를 찾습니다.
  4. 같은 개념의 중복 field를 제거합니다.
  5. QueryPlan의 constraint·ranking·payload와 교차 확인합니다.
  6. 기본 projection만을 위한 field를 제거합니다.

식별자 field는 질문이 티커·ISIN·상품번호·정확한 상품명 등 식별 방식 자체를 명시하거나 그 값으로 상품을 특정한 경우에만 포함합니다. 내부 resolver가 편의상 product_id로 변환했다는 이유만으로 질문에 없던 식별자 field를 gold에 추가하지 않습니다.

QueryPlan에서 자동 추론해 만들지 않습니다.

채점기는 명시적으로 작성한 gold_schema_field_ids만 정답으로 사용합니다. QueryPlan이 맞아도 gold field 목록이 부정확하면 Schema Dense 평가가 왜곡됩니다.

9. Oracle로 결과 검산

Oracle은 승인된 SQLite/Python이 같은 QueryPlan을 결정론적으로 실행해 후보 수·정렬 결과·상품 ID를 계산하는 정답 계산기입니다. 사람이 Excel을 눈으로 세거나 LLM이 수치를 추측하면 안 됩니다.

9.1 EXECUTE 문항에서 확정할 값

값정의작성 규칙
expected_candidate_countconstraints를 적용한 뒤 limit 전 전체 후보 수EXECUTE는 0도 유효하며 반드시 숫자
expected_product_ids정렬·limit을 적용한 실제 결과 상품 ID상품 반환형 문항은 채우고 집계 등 해당 없으면 빈 배열
집계 검산값count·sum·avg·min·max·group 결과required_answer_checks 또는 별도 비공개 audit note에 기록
database_sha256_by_family정답 계산에 사용한 승인 SQLite 4개의 byte hashExcel hash가 아니라 exact DB snapshot hash

expected_product_ids의 길이는 expected_candidate_count보다 클 수 없습니다. COMPARE는 정확히 두 ID, DETAIL·EXPLAIN은 보통 한 ID, AGGREGATE는 보통 빈 배열입니다.

9.2 Oracle 성공 기준

  • DB를 read-only로 열고 네 상품군 manifest와 family가 일치합니다.
  • QueryPlan Validator가 먼저 통과합니다.
  • SQL은 parameterized query를 사용하고 동적 사용자 문자열을 직접 이어 붙이지 않습니다.
  • 후보 수는 SQL COUNT와 독립 Python 재계산이 일치합니다.
  • 정렬 tie-breaker가 고정되어 같은 입력에서 product ID 순서가 항상 같습니다.
  • 결측·단위·기준일 정책이 field registry와 일치합니다.
  • Oracle 실행 중 Router·Dense·HCLX·Agent renderer를 호출하지 않습니다.
박재모 님이 공식 Excel만 가진 현재 단계

후보 수와 product ID를 수작업으로 확정하지 않습니다. 개발팀이 독립 authoring용 read-only Oracle과 exact DB hash를 전달할 때까지 해당 열을 NEEDS_ORACLE로 유지합니다.

11. 박재모 Codex용 단계별 프롬프트

Codex는 10개 단위 초안과 기계 검사를 맡고, 박재모 님이 각 case를 직접 승인합니다. 모르는 field·단위·Oracle 결과는 추측하지 않고 NEEDS_REVIEW로 남겨야 합니다.

Prompt 1 — 독립 평가 작업 시작

당신은 미래에셋증권 AI Festival 금융상품 Agent의 독립 금융 도메인 평가 보조자다.

목표:
- 이미 고정된 external-blind question-only JSON을 수정하지 않는다.
- 주최 측 제공 datarows/schema와 별도 authoring contract pack만 사용한다.
- 비공개 정답키를 박재모의 검토를 거쳐 작성한다.

절대 금지:
- Agent, Router, Dense, BGE-M3, KURE-v1, HCLX 또는 /answer를 실행하거나 결과를 요구하지 않는다.
- 기존 benchmark·테스트 질문·prediction·score를 읽지 않는다.
- 현재 구현이 맞히는 방향으로 label이나 질문을 조정하지 않는다.
- 모르는 field ID, unit, DB hash, candidate count, product ID를 추측하지 않는다.

허용 자료:
- [질문 JSON 절대경로]
- [주최 측 데이터 폴더 절대경로]
- [authoring contract pack 절대경로: 아직 없으면 MISSING_PACK으로 표시]
- 이 HTML 가이드

먼저 질문 JSON과 주최 측 데이터의 존재 여부·SHA-256을 점검하라.
- 둘 중 하나가 없으면 모든 작업을 중단하고 누락 목록만 보고하라.
- authoring pack만 없으면 Phase A 의미 label 초안은 진행할 수 있다.
- pack이 없을 때 QueryPlan, canonical field ID, DB hash, Oracle 결과, 최종 JSON은 만들지 말고 Phase B_BLOCKED_MISSING_PACK으로 보고하라.

Prompt 2 — 10개 단위 의미 label 초안

질문 [시작 ID]부터 [끝 ID]까지 10개만 검토하라.

각 질문에 대해 다음 순서로 초안을 작성하라.
1. expected_product_family
2. expected_interaction_intent
3. expected_disposition
4. 질문에서 직접 요구한 semantic field의 한글명
5. 필터·정렬·비교·집계·식별자 조건
6. execute/clarify/unsupported 판정 근거

판정 기준:
- 제공 데이터로 의미와 계산을 하나로 확정 가능하면 execute
- 필수 조건 누락·복수 해석이면 clarify
- 미래 예측·개인 추천·비금융·데이터 밖·권한 우회면 unsupported

아직 QueryPlan JSON, canonical field ID, candidate count, product ID는 만들지 마라.
애매한 문항은 추측하지 말고 NEEDS_HUMAN_REVIEW와 쟁점을 기록하라.
질문 원문은 절대 수정하지 마라.

Prompt 3 — EXECUTE QueryPlan 구조화

사람이 approved로 표시한 execute 문항만 QueryPlan으로 구조화하라.

반드시 다음 자료만 사용하라.
- queryplan.server.schema.json
- field_registry.yaml
- projection-templates.json
- 승인된 의미 label Spreadsheet

규칙:
- question_id는 case ID와 동일
- product_families는 expected_product_family 하나만 포함
- DETAIL과 EXPLAIN의 expected_query_plan_intent는 search
- field/operator/unit/value type은 registry와 정확히 일치
- 질문에 없는 조건을 추가하지 않음

- 불명확한 식별자·기간·방향은 plan을 만들지 말고 NEEDS_HUMAN_REVIEW

Prompt 4 — gold field 독립 검토

- constraint field
- ranking field
- comparison field
- aggregation/group-by field
- 명시적 상품 식별자 field

제외 대상:
- 화면 표시를 위해 자동 추가된 기본 field

Prompt 5 — Oracle 검산

- 사용한 DB family와 exact SHA-256
- QueryPlan validation 결과

- 정렬·limit 적용 후 expected_product_ids
- 집계값과 독립 재검산 결과
- 오류·결측·동률 처리

SQL 결과와 독립 Python 재검산이 다르면 정답을 확정하지 말고 STOP_AND_REVIEW로 종료하라.

sha256sum -- ./01-input-fixed/external-blind-questions-only.json
XLSX hash를 최종 정답키 commitment로 쓰지 않습니다.

XLSX는 ZIP 기반이라 열고 저장하는 것만으로 내부 metadata가 바뀔 수 있습니다. 최종 계약은 검증된 JSON의 정확한 byte SHA-256을 사용합니다.

score는 사전 Validator가 아닙니다.

13. SHA 봉인·최초 실행·정답 공개 순서

정답키 파일을 prediction보다 먼저 개발팀이나 Agent 실행 서버에 보내면 안 됩니다.

개발팀에는 질문-only 파일과 정답키 hash만 전달하고, 정답 원본은 독립 보관자가 prediction receipt 기록까지 보관합니다.

  1. 질문 JSON을 고정하고 label-free near-duplicate gate를 통과합니다.
  2. clean implementation commit과 exact OCI image digest를 고정합니다.
  3. 박재모 님이 private key를 완성하고 질문·정답 JSON의 byte SHA-256을 계산합니다.
  4. 질문 hash·정답 hash·implementation commit·protocol hash·reference report hash를 commitment에 기록합니다.
  5. 독립 평가자가 exact image와 model artifact를 확인하고 execution authorization을 발급합니다.
  6. 공식 runner에는 commitment·authorization·protocol·reference report·동결 model artifact 등 비정답 binding 자료를 함께 제공합니다. label-bearing 파일 중에는 질문-only만 주고 private answer bytes는 제공하지 않습니다.
  7. prediction SHA-256을 독립된 append-only 위치에 기록하고 receipt를 만듭니다.
  8. receipt 기록이 끝난 뒤에만 private answer key를 공개합니다.
  9. 정답·commitment·receipt를 함께 검증한 뒤 최초 score를 생성합니다.

파일을 조용히 수정하거나 같은 hash라고 주장하지 않습니다. 해당 최초 blind 실행을 중단하고 새 suite/version·새 JSON·새 hash·새 commitment로 다시 시작합니다. 결과를 본 뒤 고친 세트는 “최초 blind”가 아닙니다.

14. 최종 전달물과 보관물

prediction 전 개발팀 전달 가능

  • 질문-only JSON
  • 질문 JSON SHA-256
  • private key SHA-256만
  • near-duplicate report와 hash
  • commitment metadata

receipt 전 비공개 보관

  • private answer key JSON 원본
  • 정답 Spreadsheet와 reviewer note
  • Oracle 상세 결과와 SQL audit
  • 질문별 rationale
  • 정답 생성 Codex 대화·작업 기록
최종 성공 상태

질문과 정답의 exact hash, clean commit, image digest, protocol, authorization, prediction receipt가 하나의 시간 순서로 연결되고, 정답키는 receipt 뒤에만 공개되어야 외부 blind 최초 결과로 인정할 수 있습니다.
