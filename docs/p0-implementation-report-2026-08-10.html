이 프로젝트가 지키는 기본 원칙

  • 싱글턴: 질문 1개에 독립 답변 1개만 처리한다. 이전 대화에 기대지 않는다.

  • 평가·제출 LLM은 HCLX만: Qwen은 이번 작업에 사용하지 않았고 평가 경로에도 사용할 수 없다.

2. 변경 전 구현 단계

변경 전에도 금융상품 검색의 중심 구조는 이미 있었다. QueryPlan(질문을 DB가 실행할 수 있는 조건표), Oracle(SQLite/Python으로 정답을 계산하는 실행기), Verifier(결과를 다시 확인하는 재검산기), 근거·기준일 출력까지 연결돼 있었다.

질문자연어 입력
→
Router의도·상품군 분류
→
QueryPlan조건표 생성
→
OracleDB 검색·계산
→
Verifier결과 재검산
→
답변근거·기준일 포함
문제는 검색·계산 기능 자체보다 질문이 실행되기 전의 안전 검사가 충분하지 않았다는 점이다. 공격 문장, 제공 데이터 밖 상품, 모호한 조건, 잘못된 정렬 방향이 DB 실행 단계까지 내려갈 가능성이 있었고, 역질문·미지원 응답에도 부분 QueryPlan이나 상품 근거가 남을 수 있었다.

3. 핵심 수정·보완 내용

항목변경 전 문제핵심 보완변경 후 효과
SafetyEnvelope
안전 출입문		 공격 지시·실거래·실시간 정보·데이터 밖 질문을 한곳에서 선차단하지 못함 Router보다 먼저 질문을 검사해 보안 우회, 가짜·외부 상품, 주문 실행, 미래 전망, 비금융 요청 등을 차단 위험 질문이 QueryPlan·DB 실행으로 내려가기 전에 중단
Semantic Coverage Gate
의미 누락 검사		 “수익률 높은”, “규모 큰”, “안전한”처럼 기준이 여러 개인 표현이 축소 해석될 수 있음 질문의 조건이 실제 필드와 연산자로 빠짐없이 표현되는지 검사 기간·통화·지표를 확정할 수 없으면 추측 실행 대신 역질문
모호 조건·방향 보완 가나다순, 오래된/빠른 날짜, 운용규모=AUM, 제외 조건, “하나 보여줘” 등의 해석이 불완전 정렬 방향을 대상 필드와 묶고, 별칭·제외·결과 개수 표현을 보완 엉뚱한 필드 정렬과 반대 조건 실행을 줄임
Manifest
허용 데이터 목록		 DB가 스스로 일관적인지는 확인했지만, 주최 제공 파일 중 어떤 묶음을 허용할지 고정하지 않음 주최 제공 파일을 팀이 hash·크기·행 수·기준일로 고정한 manifest 추가 evaluation/production에서 다른 원천이나 변조 DB가 섞이면 시작·요청·health 단계에서 거절
Safety blind
봉인 최초 시험		 기존 공개 회귀만으로 새 공격 질문에 대한 안전성을 판단하기 어려움 192개 질문과 기대값을 실행 전에 봉인하고 최초 결과를 보존 실패를 숨기지 않고 봉인 최초 실행 70/192와 수정 후 재시험 135/192를 분리 관리
Timeout·동시성 응답 timeout 뒤 내부 작업이 계속되거나 요청이 쌓일 수 있음 전체 시간 예산과 기본 동시 실행 2개를 두고, 내부 계산과 provider에도 남은 시간을 전달 과부하 시 무한 대기열 대신 안전한 overload/timeout 응답
추가 경계 강화: Oracle 직전에 실행 권한을 한 번 더 확인한다. clarification/unsupported 같은 control 응답은 QueryPlan, 후보 수, 상품, citation, manifest 등 실행 상태를 포함할 수 없도록 DTO(외부 응답 형식) 규칙도 강화했다. 이 DTO 의미 변경은 조해영 담당 Core 계약과 연결되므로 main merge 전에 계약 리뷰와 합의가 필요하다.

현재 구현

결정론적 경로

현재 실제 /answer는 HCLX를 호출하지 않는다. SQLite/Python과 규칙 기반 renderer가 검색·계산·답변을 처리하며 provider_model=null이다.

공개 잠금

공모펀드

데이터·Oracle·Verifier 내부 경로는 구현돼 있지만, 기본 Backend에서는 공개 실행 flag가 잠겨 있다. 팀 검수와 별도 승인 전에는 실행하지 않는다.

계약만 완료

HyperCLOVA X

QueryPlan·비교 draft·근거 답변을 위한 HCLX provider(모델 호출 모듈)의 연결 규칙과 모의 통신은 있다. 실제 HCLX HTTP 통신, 인증정보, FastAPI 연결은 아직 없다.

미구현

Dense Retrieval·Re-ranker

현재는 구현하지 않았다. BM25/lexical 검색 실패가 새 blind에서 확인되고 정확도 개선과 지연 비용이 입증될 때만 추가한다.

같은 문제의 실패를 본 뒤 수정 효과를 확인한 결과다. 개선 확인에는 유용하지만 새로운 blind 점수로 발표하면 안 된다.

6. 남은 핵심 과제

가장 먼저 할 일

1
Core·DTO 계약 리뷰
조해영과 control 응답의 QueryPlan·근거 금지 규칙, timeout 오류 표현을 합의한다.
2
Staging 재검증
팀이 고정한 DB를 처음부터 다시 만드는 경우와 기존 DB를 재사용하는 경우를 모두 확인한다. 전체 테스트, 공식 모의평가, 공격 질문(red-team), 금융 도메인 QA, Docker smoke를 다시 실행해 새 평가 결과 파일로 보존하고 기존 최초 결과는 덮어쓰지 않는다.
3
신규 사람 작성 blind
박재모가 안전 경계와 도메인 정확도 질문을 새로 작성하고, 코드 freeze 후 정답을 봉인해 최초 한 번 평가한다.
4
질문 로그 보호
공식 GET query string의 평가 질문이 Uvicorn·proxy 로그에 원문으로 남지 않도록 질문 원문을 가린다. 노출 확인용 가짜 질문으로 통합 테스트한다.

제출 전에 반드시 필요한 일

우선 과제현재 상태완료 기준
실제 HCLX 연결 HCLX 연결 규칙과 모의 통신만 구현 공식 endpoint·model ID·인증 header 확인, 비밀정보를 안전하게 주입하고 실제 HCLX HTTP 통신을 Backend에 연결한다. 인증·과부하·서버 오류·timeout도 검증한다. QueryPlan 오류는 DB 실행 없이 안전 오류로 끝내고, 답변 생성 오류는 검증된 deterministic fallback(규칙 기반 대체 답변)을 사용한다.
공모펀드 공개 flag 승인 내부 기능 완료·기본 locked SEARCH/DETAIL/COMPARE/AGGREGATE/EXPLAIN 공식 GET, 통화·기준일·근거·장애 회귀 후 versioned flag 승인.
NCP Public API 현재 127.0.0.1 내부 bind 공식 인증·IP·TLS·QPS 확인, Public endpoint, 방화벽, 자동 재기동, health/alert, 평가기간 가용성 검증.
성능·응답 크기 기본 동시 실행 2로 안전 제한 NCP에서 서버 첫 실행(cold)과 재실행(warm), 동시 요청 1/2/4/8, 일반·지연 응답시간, CPU·메모리, 응답 크기, HCLX token·비용을 측정한다. 완전히 멈춘 모델 호출은 작업 프로세스를 재시작해 회수한다.
데이터 기준일 확정 설명회 7월 10일, manifest 7월 11일, 상품별 동적 기준일이 함께 존재 날짜 의미와 0·결측·판매/거래 코드 의미를 공식 schema·서면으로 확인하고 registry·근거·문서를 함께 갱신.

필요성이 확인될 때만 추가

  • 문서 RAG: 현재 BM25/SQLite FTS 최소 기능만 있다. 출처·라이선스·기준일이 승인된 실제 corpus를 확보한 뒤 연결한다.
  • Dense Retrieval·Re-ranker: 새 blind에서 의미 검색 실패가 확인되고 정확도 향상과 지연 비용이 입증될 때만 도입한다.
  • Ontology·Frontend: TTL 5개는 구현돼 있다. 금융 label 검수와 주최 형식 확인 후, 본선 시연 필요가 확정되면 얇은 UI를 연결한다.
계속 차단해야 하는 범위: 멀티턴, 실시간 시세·뉴스, 실제 주문·계좌 접근, 수익 전망·보장, 제공 데이터 밖 상품 추천, 상품군 간 근거 없는 합산은 “남은 기능”이 아니라 현재 정책상 미지원이다.
